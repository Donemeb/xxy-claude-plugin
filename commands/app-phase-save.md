name: app-phase-save
description: 根据当前对话中的项目进度变更，检查全部代码和文档，生成 CLAUDE.md 更新意见，保持统一。等待用户确认后写入
---

根据当前对话中发生的项目进度变更，更新 CLAUDE.md。

**Input**: 无需参数。自动从当前对话上下文提取变更。

**Steps**

1. **收集变更信息**

   变更范围以两个维度交叉确定：

   **维度一：对话上下文** — 回顾当前对话中讨论了什么，作为判断"哪些变更是有意义的"的信息源。

   **维度二：git 实际变更** — 运行 `git diff`、`git diff --staged`、`git status` 获取工作区中实际的增删改。以此作为变更的实际范围，不凭记忆或推测。

   两者结合：用对话上下文理解变更的语义和重要性，用 git 变更确认实际改了什么。不预设固定的变更类型清单。

2. **生成更新意见**

   整理变更，生成一份结构化的更新意见，包含：

   - **变更摘要**：一句话总结本次变更主题
   - **需要更新的章节**：列出 CLAUDE.md 中哪些章节需要改动
   - **具体改动内容**：对每个章节，用 diff 风格展示：
     ```
     ## 开发计划与进度
     
     - 旧: Phase 2 — 机器人卡片连接方式图标    ○ 待开发
     + 新: Phase 2 — 机器人卡片连接方式图标    ✅ 已完成 (2026-06-12)
     ```
   - **无需改动的章节**：明确列出不需要改动的部分，让用户确认没有遗漏

   如果当前对话没有产生需要记录的变更，直接告知用户"无变更需要更新"并结束。

   **Phase 状态标注规则**：
   - ✅ 已完成：该阶段全部工作完成且已归档
   - 🔨 开发中：正在迭代，有部分产出但未完成
   - ○ 待开发：尚未开始

   判断依据：优先依据用户的描述。如果用户说"实现了X"但未说"完成了X"，默认使用 🔨 开发中。只有用户明确表示完成时才用 ✅。

3. **等待用户确认**

   使用 AskUserQuestion 工具展示更新意见，询问用户：
   - 确认更新
   - 调整内容（用户口头说明需要改什么）
   - 取消

   **必须等待用户明确确认后才能执行下一步。**

4. **执行更新**

   用户确认后，读取当前 CLAUDE.md，使用 Edit 工具进行更新。

5. **确认完成**

   简要报告已更新的章节。

**Guardrails**

- 只更新 CLAUDE.md 中与当前对话变更直接相关的内容
- 不重构或重写无关章节
- 保持现有格式风格一致
- 技术栈版本号只在用户明确升级依赖时才更新
- 如果变更只在 spec 文件中，不重复写入 CLAUDE.md，只更新索引描述
- 不删除用户手动添加的内容
