# Skill：技术选型收敛方法

> 从分析到可执行决策的收敛过程。适用于任何技术选型场景（语言、框架、架构、存储方案等）。
> 由调用者显式触发。产出三个独立文件，互相引用。

---

## 使用方式

本方法是一套**结构化的决策收敛流程**。围绕一个选型主题，按以下节奏推进：

```
① 约束补全 —— 确认团队规模、项目状态、优先级、已有决策等前提条件
② 需求审视 —— 检查需求描述是否存在隐含假设，列出多种合理解读供决策者选择
③ 业界调研 —— 按证据等级（L1→L2→L3→L4）逐级获取业界实践证据
④ 方案对比 —— 列出至少 2 个候选方案，沿 5 个维度对比（复杂度/体验/业界采用/失效边界/回退成本）
⑤ 方向确认 —— 输出决策.md + 补充说明.md 核心章节，由决策者确认方向
⑥ 自审完善 —— 对方案执行自审六问，发现问题并入代价部分，输出补充说明.md 完整版
⑦ 影响审查 —— 检查本次决策对其他已有选型的影响，输出影响分析报告
⑧ 选型闭环 —— 所有选型完成后，依次执行完整性检查、全局一致性审查、依赖版本选型、
                技术栈总览生成、代码审查方案生成、实施参考统一生成
```

每个选型主题独立走 ①→⑦，所有选型完成后走 ⑧。各步骤的详细规则见后续章节。

---

## 最终产出物

一次完整的选型收敛流程（从第一个选型到最后一个选型全部完成）会产出以下文件：

| 文件 | 面向谁 | 内容 | 何时生成 |
|------|--------|------|---------|
| **决策.md** | 决策者、项目经理 | 一页纸的决策摘要：选了什么、不选什么、代价是什么 | 每次选型的第一阶段 |
| **补充说明.md** | 技术负责人 | 决策的完整论证：证据、对比、代价展开、自审结果 | 每次选型的第二阶段 |
| **实施参考.md** | 执行开发的工程师 | 具体实现指南：目录结构、代码示例、配置、违规表 | 所有选型结束后统一生成 |
| **依赖版本选型决策.md** | 全体技术人员 | 第三方依赖的版本锁定及兼容性验证 | 全局一致性审查后 |
| **技术栈与架构总览.md** | 全体技术人员 | 所有选型结论的汇总文档，含架构图 | 依赖版本选型后 |
| **代码审查方案.md** | 代码审查人员 | 基于选型决策的分层审查清单 | 技术栈总览后 |

## 核心认知

技术选型的目的不是"找到最优解"，而是**在约束条件下做出可追溯、可推翻的决策**。

选型过程会产生大量分析材料（对比表、基准数据、利弊清单）。这些材料对分析过程有价值，但对决策者是噪声。收敛的任务是：**把分析成果转化为三个独立文件，各自面向不同读者。**

## 启动检查：约束与前提补全

收敛开始前，**必须主动向用户确认以下信息**。不允许在信息不充分的情况下静默推进。

**必须确认的约束：**

| 约束维度 | 要问的问题 | 为什么必须问 |
|---------|-----------|------------|
| 团队规模 | 实际几个人？最理想的估计和最保守的估计？ | 决定哪些方案的投入产出比不成立 |
| 项目状态 | 新启动 / 存量维护 / 迁移重构？ | 决定是否存在既有约束（如不能改已有代码） |
| 优先级排序 | 体验优先 / 速度优先 / 成本优先？ | 决定方案取舍方向 |
| 高概率未来 | 有哪些确定但非当前优先级的事项？ | 决定是否需要为未来预留路径 |
| 已默认采用的决策 | 用户是否已经默认了某些技术前提？ | 防止循环论证——如果用户已经默认"用 Compose"，语言选型不能假装没有这个前提，必须明确标注这是外部约束而非本选型的结论 |
| 其他选型的结论是否可作为外部约束 | 本次选型是否可以引用之前收敛的结论？哪些可以、哪些不可以？ | 防止执行者自行推断选型间的"同一轮"关系。每次收敛独立启动，约束由用户显式确认 |
| 用户已提供的业界实践材料 | 项目目录或对话中有哪些用户已提供的参考材料？（如反编译源码、调研报告、竞品代码等） | 防止执行者跳过用户特意准备的材料。用户提供的材料必须全部审查，不允许以"其他证据已充分"为由跳过任何一份 |

### 选项呈现规则（强制）

向用户呈现约束/范围/解读的选项时，**必须为每个选项附带通俗解释**，让知识不足的用户也能做出合理判断。

**规则：**
1. 利用选项的 `description` 和 `preview` 字段提供解释：`description` 写一句话概括，`preview` 写通俗解释（用项目场景举例、说明选了会怎样/不选会怎样）
2. 解释内容使用通俗语言，避免未解释的术语
3. 不要将「帮我理解」作为独立的可选答案——解释嵌入在选项的 preview 中，用户浏览选项时自然看到
4. 此规则适用于：启动检查的约束确认、需求审视的多解读选择、方案选定前的对比确认

**最后一项尤其关键。** 如果用户已有默认决策（如"UI 用 Compose"），应将其标注为**外部约束**而非本选型论证的一部分。区别：

```
❌ "选 Kotlin 因为它支持 Compose"（把外部约束当成了论证）
✅ "选 Kotlin（Google 推荐，79% 采用率）。此外，团队已确定使用 Compose，
   Kotlin 是 Compose 的唯一支持语言——这是额外约束，不是选型理由。"
```

### 需求审视（强制）

启动检查不仅是"收集约束"，还包括**审视需求本身**。用户提出的需求往往隐含未被识别的假设。如果直接基于字面意思推进，可能锁定错误的方案空间。

#### 高危关键词触发清单

当需求描述中出现以下关键词时，**强制触发**三个动作：

| 高危关键词 | 风险 |
|----------|------|
| 保活、维持、持续、稳定 | 隐含"进程不能死"，但可能"短时间不丢 + 长时间重连"才是真正需求 |
| 性能、流畅、实时 | 隐含"越快越好"，但具体阈值决定方案空间 |
| 安全、可靠、不丢失 | 隐含"零容忍"，但实际可接受的失败率因场景而异 |
| 后台、电池、内存 | 系统级行为，方案空间大，错误代价高 |
| 权限、加密、合规 | 涉及系统级或法律约束，需特殊论证 |

**触发后的强制动作（缺一不可）：**

1. **隐含假设审视**——列出该需求的**所有合理解读**，标注每种解读的隐含假设，向用户确认采用哪种解读。不允许 Claude 自行选定一种解读推进
2. **业界实践调研**——按"业界实践证据等级"小节的规定执行
3. **方案对比**——按"方案对比要求"小节的规定执行

#### 隐含假设审视的方法

将用户需求拆解为多种解读，明示每种解读的隐含假设。例如：

```
用户需求："需要分钟级保活"

解读 A：进程不能被杀
        隐含假设：连接必须完全不中断
        对应方案：前台 Service / 进程保活

解读 B：短时间切出不丢 + 长时间切出可重连
        隐含假设：允许 ~5 秒重连等待
        对应方案：协议层保活 + 状态持久化 + 自动重连

解读 C：完全接受任何中断
        隐含假设：用户可手动恢复
        对应方案：不做任何保活机制

→ 必须询问用户选择哪种解读，不允许 Claude 自行决定
```

**禁止行为：**
- 禁止跳过此审视直接选定方案
- 禁止只呈现一种解读（必须列出至少 2 种）
- 禁止将"最严苛的解读"默认作为正确解读

## 禁止事项

### 禁止循环论证

选型论证必须独立成立，不能依赖同一选型中其他尚未被确认的决策。

检验方法：把被引用的决策从文档中去掉，论证是否仍然成立。如果不成立，就是循环论证。

**前提来源标注：** 列出本选型论证中引用的所有前提，逐项标注来源：

```
来源类型：
  外部约束 — 用户在启动检查中确认的已确定决策
  本次选型的中间结论 — 本选型过程中推导出的判断
  未确认的假设 — 尚未获用户确认的信息
  社区通称 — 社区对某技术的命名或归类，非官方原文
  官方原文 — 官方文档的实际措辞
  业界实践 [等级] — 同类产品的实际做法（L1/L2/L3/L4，详见"业界实践证据等级"小节）

规则：标注为"未确认的假设"的前提不能作为论证依据。
```

### 禁止信息轰炸

决策者不需要看到备选方案的完整对比矩阵、所有数据来源、每个技术细节的利弊分析。这些是分析过程的中间产物，不是决策的输入。

### 禁止以分析代替决策

列完利弊不代表做了决策。决策是"在已知利弊的情况下，基于约束条件选择一个，并明确接受其代价"。

### 禁止静默假设

不允许在信息不完整时自行假设约束条件并推进。遇到缺失信息必须向用户提问，明确获得回答后才能继续。

### 禁止跨选型继承约束

每次选型收敛独立启动，不自动继承之前收敛的约束或结论。之前收敛的结论是否可作为本次选型的外部约束，必须由用户在启动检查中显式确认。

不允许执行者自行推断选型间的关系（如"这两个选型属于同一轮"）。选型间的依赖或互斥关系由用户定义，不是执行者的判断。

### 禁止将社区解读作为官方立场

引用官方文档时，必须区分三个层次：

- **官方原文**：官方文档的实际措辞和术语
- **社区解读**：社区对官方文档的命名、归类和延伸解读
- **执行者判断**：基于以上两者的推理结论

任何标记为"官方推荐"或"官方不推荐"的主张必须能追溯到官方文档的原文措辞。如果引用的是社区的命名和归类（如社区将 Google 的 ViewModel + StateFlow 模式称为"MVVM"，但 Google 不使用此标签），必须标注为"社区通称"，不得标注为"官方"。

```
❌ "Google 官方推荐 MVVM"（Google 不使用 "MVVM" 标签，这是社区命名）
✅ "Google 推荐 UDF + ViewModel（社区通称 MVVM）"
✅ "Google 官方文档未使用 MVVM 或 MVI 标签"
```

### 禁止未验证即引用

引用 URL 作为证据时，如果该引用支撑的是影响选型方向的关键主张，必须先读取该 URL 的内容确认原文表述与引用意图一致，再写入文件。

对于不影响选型方向的辅助信息，可以标注 `[待验证]` 延后处理，但不得将未验证的内容以确定性语气呈现。

### 禁止将社区分类框架当作客观事实

当论证依赖于对技术方案的分类、归类或命名时（如"这是 MVVM"、"这是 MVI"、"这是微服务"），必须标注该分类框架的来源。如果分类框架来自社区而非官方或学术定义，不得将该框架当作客观事实使用——它只是社区的认知工具，可能简化或扭曲了实际情况。

检验方法：当文件中出现"A vs B"的对立结构时，追问"这个对立是谁定义的？A 和 B 的边界是官方/学术划定的，还是社区约定的？"如果是社区约定，标注为 `[社区分类框架]`，并检查是否存在官方实际做法落在对立面中间的情况。

### 禁止假设性业界调研

引用"业界实践"作为论证依据时，必须按"业界实践证据等级"小节的规定提供真实来源。不允许出现"业界一般做法"、"主流方案"、"同类产品通常"等无具体来源的表述。

社区讨论（Stack Overflow、Reddit、Medium 等）不得顶替真实实践证据。仅在用户明确确认不需要 L4 时，方可不附业界实践证据。详见"业界实践证据等级"小节。

### 禁止以证据充分为由跳过用户已提供的材料

当用户已提供材料（项目目录中的文件、对话中主动给出的参考资料、指定的 URL）时，**必须逐一审查**，不允许以"其他来源已提供充分证据"为由跳过。

**理由：** 用户提供的不同材料可能覆盖不同产品、不同架构选择、不同场景。Unitree Go 和 Loona 是两个不同的竞品，它们的错误处理体系可能完全不同（例如一个用 sealed class，另一个用 Exception 层次结构）。跳过任何一个都意味着丢失了用户特意准备的视角。

**检验方法：**
1. 启动选型前，扫描项目目录和对话历史，列出用户已提供的所有材料清单
2. 逐一审查每份材料中与本次选型相关的内容
3. 审查完成后才可判断"证据是否充分"
4. 如果审查后确认某份材料与本次选型无关，必须在补充说明中明确记录"[材料名] 已审查，与本次选型无关，理由：……"，不允许无声跳过

**与 L3 采信规则的关系：** L3 全部采信规则保证的是"采信时不做基本验证"，而非"可以不审查"。先审查、再采信，顺序不可颠倒。

## 业界实践证据等级

业界实践是回答"工程上合理"的证据类型，与官方文档（回答"技术上可行"）互补。涉及系统级行为决策（保活、性能、电池、权限、安全等）时，业界实践是关键证据。

调研业界实践必须按以下等级顺序获取证据。**高等级不可用时才允许降级到下一级**。

### 证据等级

| 等级 | 类型 | 含义 | 来源示例 | 标注格式 |
|------|------|------|---------|---------|
| **L1** | 官方明确陈述 | 产品方在其官方渠道**明确写出**的实现选择 | 官方技术博客、架构白皮书、官方文档中的 case study、官方工程团队公开演讲 | `[L1: <产品名> 官方技术博客 <文章标题>, URL]` |
| **L2** | 代码级证据 | 可被独立验证的实现 | 开源代码仓库（GitHub 等）、APK 反编译分析、可重现的逆向工程 | `[L2: <产品名> <版本> <文件路径>, URL 或反编译报告]` |
| **L3** | 用户提供的材料 | 用户主动提供的、来自用户自有渠道的调研材料 | 用户提供的逆向分析、用户提供的内部技术文档、用户提供的业界调研报告 | `[L3: 用户提供的 <材料描述>, 提供日期]` |
| **L4** | 社区讨论（降级） | 仅在 L1、L2、L3 均不可得时允许采用 | Stack Overflow 高票答案、Reddit 讨论串、Medium 技术文章、个人博客 | `[L4: <社区平台> <帖子标题>, URL, 访问日期]` |

### 禁止行为

1. **禁止假设性业界调研**——不允许出现"业界一般做法是 X"、"主流方案是 Y"等无具体来源的表述
2. **禁止以 L4 充当 L1/L2/L3**——社区讨论不可顶替真实实践证据
3. **禁止模糊来源**——不允许使用"某知名 App"、"开源社区中"等指代不明的表述
4. **禁止跳级降级**——必须先明确说明 L1/L2/L3 为何不可得，才允许使用 L4

### 降级判定流程

```
开始业界实践调研
  ↓
【步骤 A】扫描用户已提供的材料
  扫描项目目录和对话历史，列出用户已提供的所有材料
  ├─ 发现用户材料 → 标记为"待审查"，进入步骤 B
  └─ 未发现用户材料 → 直接进入步骤 B
      ↓
【步骤 B】查询 L1（产品官方渠道：官方技术博客、白皮书、case study）
  ├─ 找到 → 采用 L1，标注来源
  └─ 未找到
      ↓
      【强制】询问用户：是否有 L2 代码级证据或 L3 调研材料
      （例如：开源代码、APK 反编译、内部技术文档、业界调研报告）
      ├─ 用户提供 → 采用 L2 或 L3，标注来源
      │            （L3 用户提供的材料全部采信，不做基本验证）
      └─ 用户无法提供
          ↓
          明确记录"L1/L2/L3 均不可得"
          ↓
          向用户说明：是否需要降级到 L4（社区讨论）？
          ├─ 用户确认需要 → 采用 L4，标注来源 + 访问日期 + 降级原因
          ├─ 用户确认不需要 → 本次决策不含业界实践证据，在补充说明中
          │                  明确记录"用户确认不需要 L4 业界实践证据"
          └─ 用户未明确确认 → 不允许推进，等待用户决策
      ↓
【步骤 C】用户材料强制审查（无论步骤 B 结果如何）
  如果步骤 A 中发现了用户已提供的材料：
  ├─ 逐一审查每份材料中与本次选型相关的内容
  ├─ 将审查结果作为 L3 证据纳入（全部采信）
  └─ 若审查后确认某份材料与本次选型无关，
     必须在补充说明中记录"[材料名] 已审查，与本次选型无关，理由：……"
  如果步骤 A 中未发现用户材料：
  └─ 跳过此步骤
```

**关键规则：**
- **用户已提供的材料必须在调研开始时扫描，在调研结束时审查完毕**。不允许以其他证据的"充分性"跳过审查。
- **L3 全部采信**，Claude 不对用户提供的材料做基本验证——但"采信"的前提是"已审查"，未审查不得采信也不得跳过。
- **L1 未找到时，必须主动询问用户提供 L2/L3**。不允许 Claude 自行决定降级。
- **L4 是可选的，必须由用户明确确认是否需要**。Claude 不可自行决定采用 L4。

### 在补充说明.md 中的呈现要求

业界实践证据必须以独立表格呈现，不可与其他证据混排。

```
### X.Y 业界实践证据

| 等级 | 来源 | 关键事实 | 验证方式 |
|------|------|---------|---------|
| L2 | <产品名> <版本> <文件路径> | <具体事实> | <用户提供逆向分析报告 / 开源代码 URL / ...> |
| ... | ... | ... | ... |

降级说明：
  - [若使用了 L4，必须说明 L1/L2/L3 为何不可得]
  - [若未使用业界实践证据，必须说明"用户确认不需要 L4"]
```

## 方案对比要求

进入"输出三个文件"之前，必须列出**至少 2 个候选方案**并对比其代价，再选定主方案。**不允许"直接选一个方案全面推进"。**

### 触发条件（任一满足即触发）

- 需求描述命中"高危关键词触发清单"（见启动检查章节）
- 决策涉及系统级行为（保活、性能、电池、权限、安全等）
- 用户主动质疑已选方案
- 业界实践调研结果与初步方案冲突

未命中以上条件的业务层决策（如 Repository 模式、UseCase 层引入）可单方案推进，但必须在补充说明中明确记录"单方案推进的理由"。

### 对比维度

每个候选方案必须沿以下维度展开：

| 维度 | 含义 |
|------|------|
| **实现复杂度** | 新增文件数、样板代码量、依赖增加 |
| **用户体验影响** | 用户可感知的变化（等待时间、通知打扰、电量消耗等） |
| **业界采用情况** | 业界实践证据等级（L1/L2/L3/L4）+ 具体产品案例 |
| **失效边界** | 在什么场景下方案失效（如用户主动划掉、OEM 电池优化等） |
| **回退成本** | 方案被推翻时，需重写的文件数和决策联动范围 |

### 输出位置

在补充说明.md 中新增独立小节"候选方案对比"，以表格呈现：

```
### X.Z 候选方案对比

| 维度 | 方案 A：<名称> | 方案 B：<名称> | ... |
|------|---------------|---------------|-----|
| 实现复杂度 | ... | ... | ... |
| 用户体验影响 | ... | ... | ... |
| 业界采用情况 | [L2: ...] / 无 | [L1: ...] / 无 | ... |
| 失效边界 | ... | ... | ... |
| 回退成本 | ... | ... | ... |

选定方案：<A/B/...>
选定理由：<基于对比的具体判断>
```

**禁止行为：**
- 禁止只呈现一个方案（必须至少 2 个）
- 禁止把"主方案"和"不选方案"作为对比——"不选方案"是没有方案的退化情况，不是真正的候选
- 禁止"业界采用情况"维度默认留空或写"无"——必须先主动按"业界实践证据等级"小节调研
- **例外：** 若 L1/L2/L3 均不可得，且用户明确确认本次不需要 L4，可标注"无（用户确认不需要 L4 业界实践证据）"。该例外必须显式声明降级路径，不允许无声留空

## 跨选型影响审查（强制）

每次选型收敛完成后，必须主动审视本次决策对**其他已有选型决策**的影响。不允许"只产出本选型的两个文件，无视全局一致性"。

### 触发条件

阶段二（自审完成、补充说明完整版输出）后立即执行。**无论本选型是否引用其他选型的结论作为外部约束，都必须执行**——单向引用不会引起冲突，但其他选型可能反向依赖本选型的中间结论。

### 审查范围

逐项扫描已有的其他选型决策文件（决策.md 和补充说明.md，不需要审查实施参考.md）。对每个其他选型，回答：

1. **该选型的某个决策条目是否与本次新决策冲突？** ——直接冲突（结论相反）或间接冲突（前提被本次决策改变）
2. **该选型的某个代价/失效条件是否被本次决策改变？** ——原列出的代价已不存在，或失效条件已自动满足
3. **该选型的论证是否引用了本次决策涉及的技术？** ——若有，需检查引用是否仍然成立

### 输出形式

跨选型影响审查**不修改其他选型的文件**，仅向用户输出一份影响分析报告，由用户决定是否修订其他文件。理由：选型文件代表"当时的决策快照"，频繁被动修订会破坏决策的可追溯性；用户应主动评估是否需要触发其他选型的修订。

输出格式：

```
# 当前选型对其他决策的影响审查

## 已扫描的选型清单
- 选型 A：<文件名>
- 选型 B：<文件名>
- ...

## 对 <选型 A 决策> 的影响

### 直接冲突点（必须修订）
- 决策第 X 条：原文"……"与新决策结论"……"冲突
  - 冲突等级：高 / 中 / 低
  - 建议处理：<必须修订 / 建议修订 / 暂缓修订>

### 间接影响点（建议修订）
- 约束与代价第 Y 条：原"……"因新决策已失效
  - 建议处理：<必须删除 / 替换为新内容>

### 优劣分析
- 新决策对 <选型 A> 的影响优势：……
- 新决策对 <选型 A> 的影响代价：……

### 无影响
- <如某选型完全不受影响，明示"无影响">

## 对 <选型 B 决策> 的影响
...

## 修订建议汇总
| 选型 | 文件 | 修订内容 | 优先级 |
|------|------|---------|--------|
| 选型 A | 决策.md | 第 3 条重写 | 必须 |
| 选型 A | 补充说明.md | 4.2 节删除 | 必须 |
| ... | ... | ... | ... |
```

**禁止行为：**
- 禁止跳过跨选型影响审查直接进入下一个选型
- 禁止只输出"无影响"而不展示扫描过程（必须列出已扫描的选型清单）
- 禁止主动修改其他选型文件——必须由用户确认后才能修订
- 禁止将"修订其他选型文件"作为本次选型收敛的未完成事项——本次选型以补充说明完整版输出 + 影响审查报告为终点

## 三个文件

产出三个独立文件，互相引用。**实施参考.md 延后到所有选型结束后统一生成**，单次选型只输出决策.md 和补充说明.md。

### 文件一：决策摘要（面向决策者）

**篇幅：** 一段话到半页纸。可独立阅读，不依赖其他两个文件。

**格式：** 严格三段式——

```
需求：[一句话描述要解决什么问题]
决策：[选择了什么，不选什么——编号列表，每条一句话 + 可选的 1~2 句理由]
约束与代价：[这个决策的限制条件、确定的成本、触发重新评估的条件]
```

**内容归属边界（强制）：**

| 属于决策.md | 属于补充说明.md |
|------------|---------------|
| 决策结论（"选 X，不选 Y"） | 决策理由的展开论证 |
| 每条决策的一句话摘要 | 多维度对比表（复杂度/体验/业界采用/失效边界/回退成本） |
| 理由（可选，限 1~2 句） | 证据表格（L1/L2/L3/L4） |
| 约束与代价（简述） | 代价的详细展开 |
| 失效条件（一句话触发条件） | 不选方案的理由 |
| | 具体步骤编号（如"步骤 1→2→3"的初始化流程） |
| | 逐项规则表（如"允许的操作"表、"错误场景处理"表） |
| | 状态机图 / 状态转换表 |
| | 服务清单与职责表 |
| | 与已有决策的协同检查表 |
| | 自审六问结果 |

**判断原则：** 如果删掉某个表格/列表后，读者仍能对"选什么、不选什么"做出同意/不同意的判断，则该表格/列表属于补充说明.md。

**原则：**
- 只写决策和代价，不写论证过程、不写规格细节
- 数据只在用于支撑代价量化时出现（如"~79% 应用使用"、"iOS 迁移 25~40 人日"）
- 不出现代码、文件路径、构建配置、模块结构、具体步骤编号
- 不出现详细表格（状态机表、错误处理表、规则表等 → 补充说明.md）
- 读完这一段就能做出"同意/不同意"的判断

### 文件二：补充说明（面向需要理解原因的决策者或技术负责人）

**篇幅：** 1~3 页。开头引用文件一作为摘要。

**格式：** 按选型维度组织，每个维度包含——

- 证据表格：事实 + 数据 + 来源链接
- 不选方案的理由（简述，不超过两行）
- 代价的展开说明

**末尾附自审结果：** 对本选型方案的自审（按方案自审六问），作为决策者评估方案成熟度的辅助依据。自审发现的真问题必须写入代价部分，不能只在自审中出现而影响文件中消失。

**关于数据缺失的处理：**
- 有来源的数据正常引用
- 找不到明确数据的声明，标注 `[暂未找到明确数据，待补充]`，不将估算值当作确定性数据使用
- 用户可能掌握内部数据或行业经验来补充这些缺口

**原则：**
- 每个有数据的主张附来源链接
- 不出现具体实现细节（模块结构、代码示例、配置文件）
- 保持"为什么这样选"的叙述线，不是"怎么实现"的叙述线

### 文件三：实施参考（面向执行开发的工程师）

**生成时机：** 实施参考.md 在所有选型收敛完成后统一生成。**单次选型内不输出实施参考.md**。

**篇幅：** 不限。开头引用文件二作为背景。

**格式：** 按实施步骤组织——

- 模块结构 / 目录树
- 构建配置示例
- 第一步操作（具体到文件路径和改动内容）
- 迁移检查清单（如有跨阶段迁移需求）
- 常见违规与修正表

**原则：**
- 这个文件不参与决策，只服务实施
- 可以包含代码、配置、依赖列表
- 需要能让一个未参与决策过程的工程师按照文档完成实施
- 各选型的实施参考之间互相引用（如持久化实施参考引用跨模块通信实施参考的 ConnectionStateStore）

### 渐进式输出（强制）

三文件输出分多个阶段。**实施参考.md 延后到所有选型结束后统一生成**，单次选型只输出决策.md 和补充说明.md。

#### 第一阶段：方向确认（本次选型内）

输出内容：
- 决策.md（完整三段式）
- 补充说明.md 的核心章节：证据、不选方案、代价展开、候选方案对比、业界实践证据

**不输出：**
- 实施参考.md（所有选型结束后统一生成）
- 补充说明.md 的自审结果（自审在阶段二做）

**目的：** 让用户在"方向"层面确认。如果方案反转，重写成本最小。

#### 第二阶段：自审确认（本次选型内）

用户在第一阶段确认方向后，再输出：
- 补充说明.md 的完整版（含自审结果）

**不输出：**
- 实施参考.md

**触发条件：** 用户明确表示"方向确认"或对决策.md无异议。如果用户对方向有异议，回到第一阶段重做，**不进入第二阶段**。

#### 第三阶段：跨选型影响审查（本次选型收敛后立即触发）

执行"跨选型影响审查（强制）"小节的流程，输出对其他已有选型的影响分析报告。

由用户决定是否修订其他选型文件。

#### 阶段 3.5：选型完整性检查与全局一致性审查（所有选型完成后触发）

**触发条件：** 用户明确表示"所有选型已完成"或"没有更多选型了"。在进入阶段四（实施参考生成）之前必须完成。

**分为两个步骤，顺序执行：**

##### 步骤 A：遗漏检查

扫描项目需求，识别可能遗漏的选型维度。向用户输出遗漏分析报告。

**输出格式：**

```
# 选型完整性检查报告

## 已完成的选型（N 个）
- [列出所有已完成选型]

## 可能遗漏的选型

| 选型主题 | 重要程度 | 说明 | 理由 |
|---------|---------|------|------|
| XXX | 高/中/低 | 一句话说明这个选型解决什么问题 | 为什么认为可能需要 |
| YYY | ... | ... | ... |

## 不需要单独选型的维度
- [列出已覆盖的维度及其被哪个选型覆盖]
```

**遗漏识别的依据：**
- 扫描需求描述中涉及但未独立选型的技术维度
- 检查已有选型的约束与代价中是否引用了未独立选型的技术
- 对照同类 App 涉及的技术维度

**用户确认后：**
- 用户确认有遗漏 → 回到阶段一补充选型
- 用户确认无遗漏 → 进入步骤 B

##### 步骤 B：全局一致性审查

逐文件读取所有选型的决策.md 和补充说明.md，检查是否存在：
1. **直接冲突**：两个选型的结论互相矛盾
2. **前提失效**：选型 A 的论证前提被选型 B 的结论推翻
3. **术语不一致**：同一概念在不同选型中名称不同
4. **代价遗漏**：某选型的联动修订建议被记录但未执行

**输出格式：**

```
# 全局一致性审查报告

## 审查范围
- 已扫描 N 个选型的决策.md 和补充说明.md

## 冲突/不一致项

| 选型 A | 选型 B | 冲突类型 | 具体描述 | 建议处理 |
|--------|--------|---------|---------|---------|
| XXX | YYY | 前提失效 | A 中引用了 Mutex，但 B 决定不用 Mutex | 修改 A 补充说明 |
| ... | ... | ... | ... | ... |

## 无冲突的选型
- [列出确认无冲突的选型]

## 修订请求
| 文件 | 修订内容 | 理由 |
|------|---------|------|
| XXX补充说明.md | 第 Y 节修改 | 与 ZZZ 选型对齐 |
```

**用户确认后：**
- 用户同意修订 → 执行修订，确保所有文件一致
- 用户不同意 → 记录分歧，不强制修改
- 修订完成后才进入阶段 3.5.5

#### 阶段 3.5.5：依赖版本选型（全局一致性审查之后，技术栈总览之前）

**触发条件：** 阶段 3.5 步骤 B（全局一致性审查）通过，且用户确认修订完成。

**理由：** 所有技术选型已收敛且一致性已确认，此时才具备锁定版本的前提——版本选型需要知道完整的依赖清单和它们的兼容性约束。版本锁定必须在技术栈总览之前完成，因为总览文档包含依赖版本清单。

**输入：** 所有选型的决策.md 和补充说明.md 中引用的依赖。

**流程：**

1. **依赖清单收集**：从所有决策文件中提取全部第三方依赖，标注每个依赖的来源决策
2. **官方推荐版本查询**：对每个依赖查询 L1 官方源（官方文档、Release Notes、Maven Central），确定当前官方推荐版本
3. **版本兼容性验证**：验证版本组合的互相兼容性，重点检查：
   - AGP ↔ Kotlin ↔ KSP 版本链
   - AGP ↔ Gradle 版本要求
   - Hilt/Dagger ↔ AGP 版本约束
   - Compose BOM ↔ Kotlin 兼容性
   - 注解处理器（Room/Hilt）↔ KSP 版本匹配
4. **废弃库检测**：检查是否有依赖已被官方废弃或停止维护，识别替代方案
5. **输出**：`依赖版本选型决策.md`（含版本表、兼容性验证结果、失效条件）

**完成后：** 必须主动询问用户是否确认，确认后才进入阶段 3.6。不允许自动推进。

#### 阶段 3.6：技术栈与架构总览生成（所有选型完成后，实施参考之前）

**触发条件：** 阶段 3.5 步骤 B（全局一致性审查）通过，且用户确认修订完成。

**输入：** 所有选型的决策.md 和补充说明.md。

**输出：** 单一文件 `技术栈与架构总览.md`，包含以下内容（按需裁剪）：

| 章节 | 内容 |
|------|------|
| 技术栈一览 | 每个选型的结论，一行一条，附来源决策 |
| 依赖库清单 | 所有第三方依赖，附用途和来源决策 |
| 分层架构图 | ASCII 架构图，覆盖全部层级 |
| 核心数据流 | 关键数据路径（如 MVI 流、高频数据旁路） |
| 各选型关键细节 | 状态机、UseCase 清单、页面映射等（按项目实际需要组织） |
| KMP/跨平台预留 | 如适用，列出预留路径和迁移成本 |

**原则：**
- 描述"是什么"，不描述"怎么实现"（不出现代码、配置、具体步骤编号）
- 每个主张标注来源决策文件
- 架构图必须覆盖从 UI 到持久化的全部层级，包括横切关注点

**完成后：** 必须主动询问用户是否确认，确认后才进入阶段 3.7。不允许自动推进。

#### 阶段 3.7：代码审查方案生成（技术栈总览之后，实施参考之前）

**触发条件：** 阶段 3.6 输出已获用户确认。

**输入：** 所有选型的决策.md、补充说明.md 中标注为"强制"和"禁止"的规则条目。

**输出：** 单一文件 `代码审查方案.md`，包含以下内容：

| 章节 | 内容 |
|------|------|
| 审查流程 | 审查阶段划分（自动检查 / 分层审查 / 专项审查）及触发条件 |
| 全局禁止项 | 一票否决清单（从所有选型的"禁止"规则中提取） |
| 分层审查清单 | 按 UI / ViewModel / UseCase / Repository / 硬件服务 / 持久化逐层检查 |
| 专项审查 | 安全关键审查、高频数据路径审查等（按项目需要） |
| 横切审查 | DI / 测试 / 日志 / 第三方库 |
| 速查表 | 可勾选的审查清单 |

**原则：**
- 每条检查项必须标注来源决策
- 区分"必查（每次 PR）"和"按触发条件审查"
- "禁止"类规则直接列出，不需要论证

**完成后：** 必须主动询问用户是否确认，确认后才进入阶段四（实施参考生成）。不允许自动推进。

#### 第四阶段：统一实施参考生成（所有选型结束后触发）

**触发条件：** 用户明确表示"所有选型已完成"或主动要求"生成实施参考"。

输出内容：
- 批量为所有已完成选型生成实施参考.md
- 实施参考之间互相引用，统一目录结构、统一文件命名规范、统一代码风格

#### 理由

- 实施参考是投入最大的文件（含代码示例、目录结构、配置、违规表）
- 各选型的实施细节存在交叉（如持久化的 Repository 实现被 UseCase 层引用、跨模块通信的 ConnectionStateStore 被持久化引用），分散编写会导致风格不一致和重复劳动
- 单次选型结束时不生成实施参考，可以让用户更快推进下一个选型
- 如果某选型的方向被后续选型推翻，实施参考尚未编写，重写成本为零

**示例（反面）：**
```
❌ Claude 在每次选型收敛时都生成实施参考.md
   后续选型推翻了本次选型的方向
   → 实施参考重写（含 ~500 行实施代码）

✅ Claude 单次选型只输出决策.md + 补充说明.md（含自审）
   后续选型推翻方向 → 重写决策 + 补充说明，实施参考尚未编写
   所有选型收敛后，统一生成实施参考，互相引用一致
```

#### 阶段二结束后的主动询问（强制）

阶段二输出完成后，**必须主动询问用户**下一步动作。不允许默认进入下一个选型，也不允许默认开始生成实施参考。

询问内容：

```
本次 [<选型名称>] 选型已收敛完成。
跨选型影响审查报告已输出（如对 <选型 X>、<选型 Y> 有影响）。

请选择下一步：
1. 修订受影响的已有选型决策（如需要）
2. 开始下一个选型
3. 所有选型已完成（进入完整性检查与全局一致性审查）
```

**禁止行为：**
- 禁止单次选型内自动生成实施参考.md
- 禁止跳过跨选型影响审查直接进入下一个选型
- 禁止阶段二结束后不询问用户下一步动作

## 约束对选型的影响

| 约束条件 | 对选型的影响 |
|---------|------------|
| 团队 ≤ 1 人 | 排除需要多人协作才有收益的方案；排除"为未来付费"的方案（当前收益为零的投入不做） |
| 团队 ≤ 3 人 | 谨慎评估引入额外复杂度的方案（如 KMP、微服务、多模块构建） |
| 体验优先 | 排除有可测量性能损失的方案 |
| 项目新启动 | 无既有代码约束，选型自由度最高，但也意味着不能以"已有架构"作为论证前提 |
| 存量项目 | 已有技术栈是硬约束，选型必须在兼容性框架内进行 |
| 高概率未来事件 | 当前不投入，但代码组织预留最低成本迁移路径 |

## 失效条件的写法

每个决策必须附带失效条件。格式：

```
当 [具体可观测的条件] 满足时，重新评估 [具体决策]。
```

**有效的失效条件：**
- "专职 iOS 开发者加入时，重新评估是否引入 KMP"（可观测、有时间锚点）
- "Compose Multiplatform 支持视频渲染跨平台时，重新评估跨平台策略"（技术条件明确）

**无效的失效条件：**
- "团队熟悉后"（模糊，无法判断何时满足）
- "技术成熟后"（什么算成熟？没有标准）
- "需要时"（等于没有条件）

## 质量检查

收敛完成前，逐项检查：

| 检查项 | 通过标准 |
|--------|---------|
| 约束完整 | 所有约束已向用户确认，无静默假设 |
| 约束来源明确 | 外部约束（之前收敛的结论）由用户在启动检查中显式确认，非执行者自行推断 |
| 循环论证 | 每个决策的论证独立成立；外部前提已标注为约束而非论证依据 |
| 前提来源标注 | 论证中引用的所有前提已标注来源类型（外部约束 / 本次中间结论 / 社区通称 / 官方原文），未确认的假设未作为论证依据 |
| 引用验证 | 标记为"官方推荐/官方不推荐"的主张已与官方文档原文核对；非原文措辞标注为"社区通称" |
| 分类框架验证 | 文件中出现的"A vs B"对立结构已标注分类框架来源；社区构建的分类框架标注为 `[社区分类框架]`，不当作客观事实使用；已检查是否存在官方实际做法落在对立面中间的情况 |
| 业界实践证据等级 | 引用"业界实践"作为论证依据时：(1) 已按 L1→L2→L3→L4 顺序获取；(2) L1 未找到时已主动询问用户提供 L2/L3；(3) L4 由用户明确确认是否采用；(4) 每条证据已标注等级与真实来源；(5) 不存在"业界一般做法"等无具体来源的表述；(6) 涉及系统级行为决策时（保活、性能、电池、权限、安全），已尝试获取业界实践证据 |
| 用户材料审查 | (1) 已在启动检查中确认用户提供的材料清单；(2) 逐一审查了每份材料中与本次选型相关的内容；(3) 审查结果已作为 L3 证据纳入或已明确记录"已审查但无关"及理由；(4) 不存在以"其他证据充分"为由跳过用户材料的情况 |
| 需求审视 | (1) 已检查需求是否命中"高危关键词"；(2) 若命中，已列出至少 2 种合理解读；(3) 已向用户确认采用哪种解读，未由 Claude 自行选定；(4) 未出现"直接基于字面意思推进"的情况 |
| 方案对比 | (1) 已列出至少 2 个候选方案（非"主方案 vs 不选方案"）；(2) 每个方案沿 5 个维度展开（含业界采用情况）；(3) "业界采用情况"维度已按"业界实践证据等级"获取证据；(4) 若 L1/L2/L3 均不可得且用户确认不需要 L4，已显式标注"无（用户确认不需要 L4）"；(5) 单方案推进时已明确记录理由 |
| 渐进式输出 | (1) 阶段一仅输出决策.md + 补充说明.md 核心章节（不含自审）；(2) 阶段一未输出实施参考.md；(3) 用户确认方向后才进入阶段二；(4) 阶段二输出补充说明.md 完整版（含自审），仍不输出实施参考.md；(5) 阶段二结束后已主动询问用户下一步动作 |
| 跨选型影响审查 | (1) 阶段二输出完成后已执行跨选型影响审查；(2) 已列出已扫描的选型清单（即使结论为"无影响"）；(3) 已输出影响分析报告（含直接冲突点、间接影响点、优劣分析）；(4) 未主动修改其他选型文件——必须由用户确认后才能修订 |
| 完整性检查 | (1) 所有选型完成后已执行遗漏检查（阶段 3.5 步骤 A）；(2) 已扫描需求/已有选型/同类 App 识别遗漏维度；(3) 用户已确认无遗漏或已补充遗漏选型 |
| 全局一致性审查 | (1) 所有选型完成后已执行全局一致性审查（阶段 3.5 步骤 B）；(2) 逐文件读取所有决策.md 和补充说明.md；(3) 已检查直接冲突/前提失效/术语不一致/代价遗漏；(4) 已输出冲突报告 + 修订请求；(5) 用户确认修订后已执行，所有文件一致 |
| 依赖版本选型 | (1) 阶段 3.5 全局一致性审查通过后已执行依赖版本选型；(2) 已收集全部依赖并查询官方推荐版本（L1 证据）；(3) 已验证版本组合兼容性（AGP/Kotlin/KSP/Hilt 链等）；(4) 已检测废弃库并识别替代方案；(5) 输出依赖版本选型决策.md；(6) 用户已确认 |
| 技术栈总览 | (1) 依赖版本选型确认后已生成技术栈与架构总览.md；(2) 覆盖全部选型结论及依赖版本；(3) 架构图覆盖从 UI 到持久化的全部层级；(4) 用户已确认 |
| 代码审查方案 | (1) 技术栈总览确认后已生成代码审查方案.md；(2) 提取了所有选型的"强制"和"禁止"规则；(3) 每条检查项标注了来源决策；(4) 区分了"必查"和"按触发条件审查"；(5) 用户已确认 |
| 实施参考延后 | (1) 单次选型内未输出实施参考.md；(2) 实施参考仅在用户明确触发（所有选型结束 + 完整性检查 + 全局一致性审查 + 技术栈总览 + 代码审查方案均通过后）时统一生成；(3) 各选型的实施参考之间互相引用一致 |
| 读者匹配 | 决策者在文件一中看不到构建配置、代码示例；实施者在文件三中能找到第一步操作 |
| 代价诚实 | 每个决策都列出了确定性成本，不是只列好处 |
| 失效条件 | 每个决策有可观测的、明确的推翻触发条件 |
| 数据诚实 | 有来源的数据附链接；无来源的标注 `[待补充]`，不伪装为确定性数据；关键主张的引用 URL 已验证原文 |
| 自审完成 | 方案自审六问已回答，发现的问题已合并入代价部分 |
| 独立可读 | 文件一可独立阅读，不需要打开文件二或文件三就能理解决策 |
| 文件引用 | 三个文件之间有互相引用关系，读者可按需跳转 |

## 方案自审六问（收敛步骤 8 使用）

提出任何方案后，强制回答以下问题：

1. **第一步改什么文件？** 具体到文件路径、方法名、改什么。答不出 = 方案不可执行。
2. **改动影响多少个现有文件？** 超过 30% 是重写不是改进。
3. **新方案引入了什么新问题？** 每个方案解决一些问题的同时引入新问题，诚实列出。
4. **三年后的新人能理解吗？** 如果需要问架构师 = 隐性知识太多。
5. **只做 20% 能拿到 80% 收益吗？** 如果不能 = 问题不在架构层面。
6. **什么条件下推翻？** 写不出失效条件 = 把选择当信仰了。
