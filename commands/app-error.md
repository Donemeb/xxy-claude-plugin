## 流程

收到用户报告的问题或错误后，按以下阶段依次执行。
每个阶段必须将结论或方案提交给用户，收到明确确认后才能进入下一阶段。
禁止静默推进。

### 阶段 1：定位原因

根据用户提供的信息调查代码，定位根因。

用户可能只描述了异常行为（如"点一下就崩了"），不一定有完整的错误日志。
此时应：

1. 根据行为描述，在相关代码中排查可能的原因
2. 如果信息不足以定位，明确告知用户需要什么信息（如 Logcat 日志、崩溃堆栈、复现步骤），并说明如何获取
3. 拿到信息后继续排查

输出格式：
- 根因描述（一句话）
- 涉及的文件和代码行
- 为什么会发生

提交给用户，等待确认。

### 阶段 2：修复方案

提出最小范围的修复方案。

修复应严格局限于问题本身，避免修改范围扩散。
修改范围扩散可能引入不可预知的连锁后果。
只改必须改的，不改"顺便可以改的"。

包含：
- 要修改的文件和代码（精确到行）
- 修改内容说明
- 不修改什么，以及为什么不修改

提交给用户，等待确认后才执行修改。

### 阶段 3：排查同类

在代码库中搜索是否存在相同的错误模式：
- 搜索相关的 API 调用或代码模式
- 逐条列出发现，标注是否需要修复

提交给用户，等待确认。

### 阶段 4：预防方案

讨论如何防止同类问题再次出现。

首先根据错误性质分类，不同类型适用不同的预防手段：

| 错误类型 | 特征 | 首选预防方式 |
|---------|------|------------|
| 语法/类型/API 误用 | 编译器或 linter 能捕获 | 代码审查 |
| 状态覆盖不完整 | 语法正确、类型正确，特定状态序列下行为错误 | 单元测试 |
| 边界条件遗漏 | 正常路径正确，极端输入/时序下失败 | 单元测试 |
| 架构/设计缺陷 | 问题跨多层、需要结构性调整 | 设计文档 + 代码审查 |

根据分类结果：
- **代码审查**：提出具体审查条目，加入 `docs/软件决策与约束/代码审查方案.md` 对应章节
- **单元测试**：提出测试方案（覆盖哪些状态路径），在对应 Test 文件中添加用例
- **两者结合**：说明各自拦截的范围

说明方案的适用范围和局限性。

提交给用户，讨论确认后实施。

### 阶段 5：实施预防

根据用户确认的预防方案执行修改。

完成后汇总本次错误处理的全部变更，提交给用户。

### 结束条件

- 所有阶段完成且用户确认
- 用户明确表示结束
- 任意阶段用户表示"到此为止"
