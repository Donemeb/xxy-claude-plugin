## 目的

`docs/README/` 是给新人（熟悉编程但不熟 Android/Kotlin）的软工文档，目标是让其能脱离 AI 纯手动开发。文档一旦与代码脱节就失去价值——本命令的**唯一职责是消除过时**，不是重写。

**最高原则：代码是唯一事实来源。** 文档里任何与代码不一致的描述都是 bug，必须改文档而非迁就旧描述。

## 不可违背的约束

1. **以代码为准**：每一条要改/要留的判断，都必须基于当场读到的真实代码，**禁止凭记忆或旧文档下结论**。
2. **最小改动**：只修"过时"和"错误"，**不动**已经正确的内容。不借机重写、不"顺手优化"措辞、不重排结构。正确但写得一般的段落保留原样。
3. **每阶段用户确认**：差异清单、更新方案、写入，三道门每道都要用户明确同意才推进。**禁止静默写入**。
4. **不删用户手动加的内容**：文档里人工补充的备注/示例/坑记录，除非用户明确要求，否则保留。
5. **PlantUML 必须可渲染**：任何图表改动后，校验 `@startuml/@enduml` 配对、无破坏语法（`__ {...} __`、引号内嵌 stereotype、类成员里的字面 `\n` 等）。
6. **保留文档既定质量标准**（仅对**新增**内容生效，不以此为由重写既有内容）：
   - 中文撰写
   - 目标读者：会编程但不熟 Android/Kotlin
   - 能支撑脱离 AI 的纯手动开发（讲清"是什么/为什么/怎么改"）
   - 关键结构配 PlantUML（类图/时序图/状态图/组件图）

## 流程

### 阶段 0：确定更新范围

与用户确认本次更新的粒度：

- **全量扫描**：对全部 11 个文档逐一比对代码（默认，首次或久未更新时用）。
- **定向更新**：用户指定范围（如"只更遥控页""只更配网流程""我刚改了 BLE 层"）。

若用户未指定，默认**全量扫描**，但允许用户收窄。

---

### 阶段 1：差异扫描（代码 ↔ 文档）★ 核心

**禁止跳过本阶段直接改文档。** 必须先把"代码现状"摸清，再对照文档列出差异。

#### 1.1 摸清代码现状（用工具，不靠记忆）

按以下顺序采样代码，**记录实际值**：

| 检查项 | 怎么查 | 关注变化 |
|--------|--------|---------|
| 目录结构 | `Glob "**/*.kt"`（排除 `docs/参考demo/`）对比文档里的目录树 | 新增/删除/移动的文件或包 |
| 构建配置 | `Read app/build.gradle.kts`、`gradle/libs.versions.toml`、`app/src/main/AndroidManifest.xml` | SDK 版本、依赖、权限、applicationId、buildConfig、构建类型 |
| 入口 | `Read MainActivity.kt`、`RobotApp.kt` | 入口 Activity、横屏锁定、configChanges |
| 路由 | `Read ui/navigation/Route.kt`、`AppNavigation.kt` | 路由分支增减、参数、跳转逻辑 |
| 各层类清单 | 逐个 `Read` domain/data/infrastructure/service/ui/di 下的 kt 文件 | 类/接口/方法签名/字段/常量/密封类分支 |
| MVI 三件套 | 每个页面读 `*Intent.kt`/`*UiState.kt`/`*ViewModel.kt` | Intent 分支、UiState 字段、reduce 逻辑 |
| Stub/TODO 状态 | `Grep "TODO|Stub|占位|placeholder"` + 读对应实现 | 占位是否已实现（最易过时！） |
| 测试 | `Glob` test/androidTest 下 kt 文件 | 测试增减、覆盖范围 |
| 阶段进度 | `Read CLAUDE.md` 的"开发计划与进度"节 | Phase 状态变化 |

> 高效做法：对"逐文件精读"用 `Agent(Explore)` 并行分派（按层分包），既快又全。但**结论必须回到主线程逐条核对**，不能盲信代理摘要。

#### 1.2 逐文档对照，产出差异清单

对每个文档，逐条核对它的事实性陈述与代码现状。重点排查以下"过时高发区"：

| 过时类型 | 典型症状 | 核对方法 |
|---------|---------|---------|
| **结构漂移** | 文档画的目录树/类图里有代码中已不存在的文件；或代码新增的文件文档没提 | 目录树 vs Glob 结果 |
| **签名漂移** | 文档写的方法签名/字段/常量值与代码不符 | 读代码逐字段比 |
| **状态机漂移** | sealed class 分支增减；状态转移条件变了 | 读密封类定义 + 转移逻辑 |
| **Stub/占位已实现** | 文档标"TODO/占位/Stub"，但代码已实现真功能（**最危险**，误导新人） | grep + 读实现体 |
| **流程漂移** | 时序图里的调用顺序/参与者与代码不符 | 跟着代码重走一遍流程 |
| **配置漂移** | 版本号/SDK/依赖/权限变了 | 读 build.gradle.kts + toml + manifest |
| **进度漂移** | Phase 状态、归档变更数变了 | 读 CLAUDE.md + `openspec/changes/archive/` |

#### 1.3 输出差异清单（必须等用户确认）

按下表输出，**逐条等用户勾选**。用户可：全改 / 部分改 / 跳过 / 补充。

| # | 文档 | 位置（章节/行） | 文档现述 | 代码实况 | 差异类型 | 建议动作 |
|---|------|---------------|---------|---------|---------|---------|

- "建议动作"只写"修正/补充/删除图表中X/新增Y小节"，**不展开具体文字**（那是阶段 2 的事）。
- 若某文档完全无差异，明确标注"✅ 无过时"，不要硬凑。

提交清单，等待用户确认要改哪些。

---

### 阶段 2：提出具体更新方案

对用户确认要改的每条差异，给出**精确到文件和章节的 old→new**：

- **修正类**：贴出文档原句（old）→ 改后句（new），说明改的理由（引用代码 `文件:行`）。
- **补充类**：写明插入到哪个文档哪节之后，给出新增段落/表格/PlantUML 草稿。
- **删除类**：写明删哪段/哪个图，以及为什么不删会误导。
- **图表类**：若 PlantUML 图内容过时（如类图多了/少了类、时序图步骤变了），给出整段重写的 `@startuml...@enduml`。

原则复核（再次自检，防止范围蔓延）：
- 每条改动是否都**直接对应**阶段 1 的某条差异？没有对应差异的改动删掉。
- 是否动了"正确但措辞一般"的段落？如果有，撤回。
- 新增内容是否满足"质量标准"（中文/面向新人/PlantUML）？

提交方案，等待用户逐条或整体确认后才写入。

---

### 阶段 3：执行更新 + PlantUML 校验

对用户确认的方案，用 `Edit`/`Write` 落盘。落盘后立即自检：

1. **PlantUML 健康**：
   - 每个文档 `grep -c '@startuml'` == `grep -c '@enduml'`（配对）
   - 无破坏语法：`grep '__ {.*} __'`、`grep 'class "[^"]*<<[^>]*>>[^"]*" as'`、类成员里无字面 `\n`
   - 改动过的图，脑内或工具渲染一遍确认结构正确
2. **交叉引用**：`README.md` 索引里的文件名/链接是否仍指向存在的文档；文档间的"见 [08]"等引用是否仍有效。
3. **范围审计**：`git diff docs/README/` 看实际改动行，确认没有阶段外改动混入。

若自检发现问题，先修再继续。

---

### 阶段 4：一致性验证 + 汇总

#### 4.1 抽样回验

从本次改动里随机抽 3–5 条事实性陈述，当场重新读代码确认"文档现在说的 == 代码现在这样"。任何一条对不上，回到阶段 2 补修。

#### 4.2 汇总输出

```
## 文档更新汇总

**扫描范围**：<全量 / 定向：xxx>
**代码采样**：<读了哪些关键文件/用了几个 Explore 代理>

**差异总数**：N 条（结构漂移 x / 签名漂移 y / Stub已实现 z / ...）

**已更新**：
- docs/README/0X-xxx.md：<改了什么，对应哪条差异>
- ...

**用户跳过/否决**：<列出来，备忘>

**仍存在的已知 TODO/占位**（文档已如实标注，非过时）：
- <如：ControlService 仍为 Stub；配网 IP 占位 0.0.0.0；滑屏摇杆未实现>

**PlantUML 校验**：✅ 全部 start/end 配对，无破坏语法
**抽样回验**：✅ x/y 条核对一致
```

## 与其他命令的边界

- `/xxy:app-change-codereview`：审查 git 变更代码本身的质量。本命令是更新文档。
- `/xxy:app-change-save`：把刚做完的工作沉淀成知识（CLAUDE.md/代码审查方案）。本命令是修文档过时，**不产生新知识**——但如果在扫描中发现"文档没覆盖的新增功能"，提示用户考虑走 `/xxy:app-change-save` 补沉淀，本命令不越俎代庖。
- `/xxy:app-error`：bug 处理。修 bug 导致代码变化后，可顺手调用本命令同步文档。

## 何时调用

- 完成一个 OpenSpec change 并归档后（代码动了，文档可能过时）
- Phase 推进、Stub 替换为真实实现后
- 重构（改包名/挪文件/改签名）后
- 定期（如每月）体检
- 用户主动喊"更新一下文档"/"文档是不是过时了"
