为某项技术/方案决策的落地生成**两份递进的开发文档**：一份上手指南、一份细化手册。本 skill 从一次成功实践（WebRTC 局域网控制通道：`docs/robot-control/WebRTC控制通道开发指南.md` + `…手册-细化.md`）中提炼出**通用方法论**，不绑定场景与技术栈——通信通道、存储方案、UI 架构重写、引入新框架等任何技术落地均可套用，换实践参考即可。文中 WebRTC 仅作为方法论的**实践参考**出现，不是方法论本身。

---

## 何时使用

用户出现以下任一意图时触发：

1. **"决定用 X 实现 Y，给出详细指导 + 官方参考，让没接触过的人上手"** → 产出《开发指南》
2. **"根据指南 + 参考材料 + 项目代码和约束，给出细化到每个类/函数、新手可上手、每阶段可验证的开发流程"** → 产出《开发手册-细化》
3. 一次性走完两阶段 → 先指南后手册

可一次走完，也可分两次（先指南、用户确认后再手册）。**手册必须以指南为前置阅读**，不重复概念。

二者互补：指南建认知，手册给步骤。**手册不复述指南的概念**，只在开头链回指南。

| 5 | **项目代码骨架**（接口 / Repository / 状态机 / 领域模型 / Stub 占位） | 文档围绕「换底」组织的锚点 | `ControlService.kt` / `StubControlService.kt` / `ConnectionState.kt` |

## 核心方法论（10 条，贯穿两阶段）

每条均为通用方法，括注给出 WebRTC 案例仅作实践参考：

1. **两阶段递进，职责互补** — 指南建认知（why + 概念 + 官方参考 + 避坑全表 + 验证路线），手册给步骤（类/函数级 + 每阶段可验证）。手册以指南为前置阅读，不重复概念。

2. **以现有代码骨架为锚（"换底"思想）** — 文档不从零设计，而是「把占位/旧实现替换为真实实现」。先识别现有抽象层（接口 / Repository / 状态机 / 领域模型 / 已搭骨架），全程用「现有抽象 → 真实实现要做什么 / 不动什么」映射表组织，明确标注上层零改动。
   - *实践参考*：手册「与现有代码映射」+「对接点」表，标清 `ControlComposer`/`RemoteControlViewModel` **不动**，只换 `StubControlService` → `WebRtcControlService`。

3. **参考材料差异化管理** — 三类参考用途不同，不可混用：
   - 决策文档（why）→ 指南前置阅读
   - 真实先例详解（工业级长什么样）→ 分层模型 + 接口契约参照
   - 可跑 demo（能跑的工程）→ 可复用代码文件，逐文件标 ★ 评级
   - **必须显式说明「本项目与参考 demo 的差异在哪、为什么改」**。
   - *实践参考*：信令从 demo 的 WebSocket 换成 HTTP /offer，理由是零云依赖。

4. **从假到真的验证路线**（变量递增）— 依赖冒烟 → 本地自连/loopback → 假依赖/桩 → 真集成 → 边界/安全 → 可选项。每阶段独立可验证，前一阶段不过不进下一阶段。指南给路线总览，手册每阶段给具体验证（含期望输出）。
   - *实践参考*：冒烟（createOffer 出 SDP）→ loopback → 假机器人（aiortc）→ 真机器人 → 拔网线验心跳超时停。

5. **概念先行 + 类比驱动** — 指南开头先建心智模型：一句话定义 + 生活类比 + N 个核心概念 + 「为什么没标准答案」（若该技术存在设计自由度）。面向零基础读者。
   - *实践参考*：用「打电话」类比 PeerConnection/信令/ICE；解释「信令为何不规范化」让读者理解设计空间。

6. **每阶段四段式**（手册核心结构）— 每个阶段必须含：① 目标（一句话产出什么）② 新建类/改动（完整可粘代码，含 package/import/KDoc）③ 实现要点（避坑 inline 标编号）④ 验证（命令 + 期望输出 + 单测 + 假依赖期望）。

7. **避坑清单贯穿三处** — 指南：完整避坑表（坑 / 正确做法）；手册：速查表（坑 / 正确做法 / **对应阶段**）；代码注释：inline 标「避坑 #N」。编号跨两份文档一致。

8. **约束对齐** — 所有代码服从项目既有约束（从 `CLAUDE.md` 提取）：架构模式、DI（`@Singleton` 服务 / `@Qualifier` debug 切换 / `BuildConfig.DEBUG` 隔离）、异步（Coroutines/Flow，热流解耦订阅与生命周期，suspend 转换异步回调）、错误（统一 Result 包装，不抛裸异常到 UI）、日志（项目日志工具，不删用户已有 log）、序列化（DTO 不污染领域模型）。

9. **依赖当前状态核对**（不盲从决策文档）— 决策文档说「已引入」但 gradle 实际没引入 → 如实标「⚠️ 当前尚未引入，第一步必须先加」。占位实现（Stub）存在 → 文档围绕「替换 Stub」组织。
   - *实践参考*：指南 §4 开头核对「决策文档写已在技术栈，但 `libs.versions.toml` 实际未引入」。

10. **外部协作契约固化** — 凡涉及外部团队/系统/对端的接口、协议、数据格式、阈值等，固化为「交付契约」一节。外部实现由谁交付、选型待定项标 `TBC`。无外部协作方时此条可省略。
    - *实践参考*：给硬件团队的 5 条契约（信令 / label / JSON / 视频 / 心跳）。

## 阶段一：生成《开发指南》

### 结构模板（顺序参考，按技术特性裁剪）

1. **心智模型：X 是什么** — 一句话定义 + 类比表 + N 个核心概念（每个概念配「本项目用途」列）+ 「为什么没标准答案」（若该技术存在设计自由度）。
2. **本项目的用法与架构落点** — 一图总览（ASCII 架构图，标清各端/各层 + 关键交互）+ 「与现有代码骨架的映射表」（现有抽象 / 位置 / 真实实现要做什么）。
3. **核心流程**（交互/数据/协商流程）— 先澄清「本项目和参考 demo 流程不一样在哪、为什么」→ 选定方案 → 时序图（Mermaid `sequenceDiagram`，含异常分支）→ 报文/数据格式示例。
4. **第一步：引入依赖（⚠️ 核对当前状态）** — 先核对 gradle/manifest 实际状态，再给依赖追加 + 权限/配置 + 验证依赖到位的命令。
5. **分步实现（slice by slice）** — 从假到真、先核心后可选。每个 slice 一段代码 + 一句要点。建议「先核心链路跑通端到端，再加可选能力」。
6. **外部协作对接（如有）** — 职责清单表 + 实现选型表（标 TBC）+ 交付契约（固化为文档）。无外部协作方时省略本节。
7. **官方参考与进阶资料** — 分组：规范与核心概念 / 本项目所用库（仓库+制品仓库）/ 底层来源 / 同构范式 / 外部方候选实现 / 真实先例。
8. **新人常见坑（避坑清单）** — 完整表：# / 坑 / 正确做法。每条对应手册某阶段。
9. **落地验证路线** — 从假到真编号步骤，每步标「验证什么 / 依赖 / 对应手册阶段」。
10. **本仓库可复用资源** — 参考 demo 逐文件复用价值表（★★★/★★/★ 评级 + 「直接复用价值」一句话）。

### 撰写规则

- 面向**未接触过**该技术的读者，概念先于代码。
- 每个「避坑」要在后续手册里有对应阶段的落地。
- 任何「决策文档说 X 但实际 Y」的矛盾必须显式标注，不静默选一方。
- 官方链接给具体规范编号 / 仓库 URL / 制品坐标，不给「搜索一下」。

## 阶段二：生成《开发手册-细化》

### 结构模板（阶段制）

1. **总览** — 分层架构图（标「已有不动」vs「新建」）+ 新建文件位置树 + 前置接口扩展说明（如需扩接口，在阶段 0 做）。
2. **阶段 0：依赖 + 配置 + 接口扩展** — 引入库 + 权限/配置 + 必要的接口扩展（如接口加方法）+ Stub 同步实现新方法 + 验证编译/测试通过。
3. **阶段 1~N：每阶段四段式**（见下）。
4. **验证路线总览** — 表格：步骤 / 验证内容 / 依赖 / 对应阶段。
5. **与现有代码对接点** — 表格：现有代码 / 真实实现要做什么 / 不动。末尾点明「换底」价值。
6. **避坑清单速查** — 表格：# / 坑 / 正确做法 / 对应阶段。

### 每阶段四段式（强制）

```
### 阶段 N：<名称>
**目标**：<一句话，本阶段产出什么、到什么程度算完成>

### 新建类 / 改动：`<文件路径>`
<完整可粘代码：package + import + 类/函数 + KDoc 注释>

### 实现要点
- <逐条要点，避坑处 inline 标「避坑 #N」>

### 验证
- <可执行命令：gradlew / curl / adb logcat -s TAG:V>
- <期望输出：具体 logcat 行 / 终端输出 / UI 状态>
- <单测点名，或假依赖脚本片段>
```

### 代码规范（手册里的代码）

- **完整可粘**：`package` + 全部 `import` + 类/函数体 + KDoc。读者复制即能用，不要 `// ...省略` 关键部分。
- **对齐项目约束**：`@Singleton`/`@Inject`、统一 Result 包装、项目日志工具、`CoroutineScope(SupervisorJob()+Dispatchers.Default)`、资源 `try/finally` 释放。
- **避坑 inline 标注**：代码注释里写「避坑 #N」（与指南避坑表编号一致）。
- **TODO/占位如实标注**：当前是 Stub/占位的 → 注释标 `// TODO: 真实实现要扩字段`，不假装已完成。
- *实践参考*：阶段 4 `WebRtcControlService.connect` 是完整多步编排，`PeerConnection.Observer` 全回调列出（空实现也写并标注理由）。

### 验证规范

- 命令必须可执行（`./gradlew :app:dependencies | grep <lib>`、`curl …`、`adb logcat -s TAG:V`）。
- 期望输出必须具体（贴 logcat 行、贴假依赖终端输出、贴 UI 文案），不要写「应该能看到成功」。
- 假依赖给可跑片段（脚本等），让读者本地能起。
- 边界/安全验证单独成项（如断网/异常输入 → 系统应有的兜底行为）。

## 两阶段衔接

- 手册开头「前置阅读（必读）」第一条链回指南。
- 手册**不重复**指南的概念解释、避坑全表、官方参考——只在「避坑速查」表里链回指南对应章节，并加「对应阶段」列。
- 指南的 slice 与手册的阶段**大体对应但可重组**：指南按「认知顺序」分 slice，手册按「实现+验证顺序」分阶段（含阶段 0 依赖/接口扩展）。
- 两份文档的避坑**编号一致**（指南 #1 = 手册 #1）。

## 约束与红线

1. **禁止凭印象写** — 所有技术细节（API 签名、UUID、报文格式、常量值、版本号）必须来自代码 / 参考文档 / 官方资料，不允许用通用知识填充。
2. **禁止只画 happy path** — 时序图、流程图必须含失败 / 超时 / 取消 / 异常分支。
3. **禁止省略验证** — 手册每个阶段必须有可执行验证 + 期望输出；没验证手段的阶段要补「如何手动触发」。
4. **禁止造 UUID/报文/常量** — 从代码或契约文档提取实际值；占位/TODO 如实标注。
5. **禁止破坏现有抽象** — 文档围绕「换底」组织；上层已定接口不改，除非阶段 0 明确扩接口并说明理由 + Stub 同步。
6. **禁止掩盖不确定性** — 决策与实现不一致、外部选型未定时，标 `⚠️ 待验证` / `TBC`，不静默选一方。
7. **禁止删用户已有 log / 改超出文档范围的代码** — 本 skill 只生成文档，不改源码（文档里的代码是给读者照写的范例，不是直接落盘的 patch）。
8. **章节编号连续** — 新增章节后检查编号；避坑编号跨两份文档一致。
