针对某个设计问题，**系统调研多个成熟业界实现**的处理方式，多家对照得出**共识**（都这么做）与**短板**（都没做好），为自己的设计提供参照——**抄共识、避短板、明确超越点**。本 skill 是一套"调研借鉴"的纪律，解决"凭空设计重复造轮子""抄了业界的坑""把业界短板当共识"三类问题。方法论通用，不绑定场景与技术栈。

---

## 何时使用

- 用户问"业界 / 别人 / 成熟产品怎么做 X""这个设计有没有现成做法""有没有可参考的"
- 设计决策前，想看成熟产品如何处理同类问题，再决定自己怎么做
- 对自己的方案没把握，想用业界实践做交叉验证
- 判断某个做法是"业界共识"还是"某家无奈之举"

**不用**：纯事实查询、自己两个选项的对比选型（那是 `deep-comparison-analysis`）、不需要外部参照的内部决策。

## 核心问题：为什么要调研业界

自己拍脑袋设计，三类典型损失：

| 损失 | 表现 | 调研能补什么 |
|------|------|-------------|
| 重复造轮子 | 自己想出的"新"方案，业界早有成熟做法 | **共识**：业界趋同的做法，验证过、可直接抄 |
| 抄了业界的坑 | 照搬某一家做法，连带它的短板也抄进来 | **短板**：各家都没做好、靠某侧兜底的地方，你要超越 |
| 错把短板当共识 | 看到两家都"没做某事"，以为该这么做，其实是它们都没解决好 | **区分共识与短板**：都这么做且做得好=共识；都这么做但做得糙/靠兜底=短板 |

调研的产出不是"照抄某一家"，而是**对照多家后提炼出"该抄什么、该避什么、该自创什么"**。

## 方法论（六步）

### ① 聚焦问题

把要解决的设计问题表述成**一个可调研的问句**——问得具体，才能对照。

- 反例（太泛）："业界怎么做遥控？" → 没法对照。
- 正例（具体）："切换控制模式时，上一模式控制的维度如何可靠归零停止？" → 可对照各家具体做法。
- 检验：这个问题能否直接拿去问"X 产品是怎么做的"，且答案可比较。

### ② 选对照对象

挑 **2–3 个成熟业界实现**作为对照对象——同品类（解决同类问题）或同类问题（不同品类但问题结构相同）。

- 同品类：直接竞品（都在解决同一问题）。
- 同类问题：跨品类但问题结构相同（如"离散事件 vs 连续流"在协议设计、UI 事件、消息队列里都出现）。
- 选成熟产品：经过大规模验证的，比小众/实验性项目更有参考价值。
- 2–3 个够了：少了没对照、多了噪声。

### ③ 系统采集证据（本 skill 的核心）

针对每个对照对象，**逐个挖它怎么处理该问题**，关键是**带证据 + 严格区分"能证实 vs 推测/看不到"**。

- **证据采集手段**（按对象可得性选）：读源码（开源 / 反编译）、读官方文档与规格、读技术博客与论文、公开资料检索、直接问维护者。
- **带证据**：每条结论附"证据出处"（文件:行 / 文档段落 / 规格条款），不空口断言。
- **区分能证实 vs 推测**（关键纪律）：
  - 能证实：源码/文档直接看到的逻辑。
  - 推测/看不到：被混淆、在不可见的层（前端调后端、客户端调服务端）、或从行为反推。
  - 必须标注每条结论是"证实"还是"推测"，不把推测当事实。**这一步决定对照表的可信度。**
- 典型坑：看到某变量被赋值就当它起作用（实际可能是死代码）；看不到某逻辑就当它不存在（可能在不可见的层）。

### ④ 多家对照表

把采集到的证据铺成**对象 × 维度**的对照表。维度从问题本身分解出来（如"触发路径 / 反馈机制 / 期间锁定 / 冲突仲裁 / 取消"）。

- 每格填"该对象在该维度的具体做法 + 证据强度（证实/推测）"。
- 对照表的价值在于**横向可比**：同一个维度，三家各怎么做，一眼看出异同。
- 表里不要只写结论，要带"怎么做"的机制（便于判断抄/避）。

### ⑤ 提炼共识与短板

从对照表里提炼出两类：

- **共识**：多家趋同的做法（如"都走独立路径""都用某个机制"）——业界验证过，通常是该抄的。
- **短板**：多家都没做好、靠某侧兜底、或做得糙的地方（如"都没有完成反馈""都不锁输入靠某侧仲裁"）——这是你要**超越**的，不是要抄的。
- **区分**：判断一个"多家都这样"是共识还是短板，看"这样做对不对"——做得好且合理=共识；做得糙/留隐患=短板。
- 警惕：别把"某家的特殊选择"当共识（可能只是一家权衡）；也别把"多家共同的短板"当共识（那是它们都没解决好）。

### ⑥ 建议三档

基于共识与短板，给出三档建议：

| 档 | 含义 | 例子 |
|----|------|------|
| **抄**（共识） | 业界验证过、做得好的，直接采用 | "动作走独立离散路径"——两家共识，抄 |
| **避**（超越短板） | 业界都没做好的，明确你要超越的点 | "加开始/结束反馈 + 期间锁定"——两家都糙，你要做稳 |
| **自创**（无先例） | 业界都没解决的，标注需自创、不期待参照 | "手机不可控维度的归零语义"——业界回避了，你得自己定 |

> 三档建议是本 skill 区别于"照抄某一家"的核心产出——**不是回到业界水平，而是站在业界肩膀上明确超越点。**

```

## 0. 聚焦问题
{一个可调研的问句}

## 1. 对照对象
- 对象 A：{成熟实现}（证据可得性：源码/文档/...）
- 对象 B：...
- 对象 C（可选）：...

## 2. 证据采集（逐对象，标注 证实/推测）
### 对象 A
- 维度1：{做法}（证据：文件:行 / 文档段 —— 证实/推测）
- ...

## 3. 多家对照表
| 维度 | 对象 A | 对象 B | 对象 C |
|------|--------|--------|--------|
| 触发路径 | ... | ... | ... |
| 反馈 | ... | ... | ... |
| ... | ... | ... | ... |

## 4. 共识与短板
- 共识（该抄）：...
- 短板（该超越）：...

## 5. 建议（抄 / 避 / 自创）
- 抄：{业界共识}
- 避（超越）：{业界短板，你要做稳的点}
- 自创：{业界无先例，需自己定的}
```

## 与其他 skill 的关系

- **与 `deep-comparison-analysis` 区分**（被其链接）：`deep-comparison-analysis` 是"对比**自己的两个选项**并收敛选一个"（我选 A 还是 B）；本 skill 是"调研**外部多个成熟业界实现**借鉴"（别人怎么做我参考）。对象不同（自己选项 vs 外部业界）、目的不同（选一个 vs 抄/避/超越）。选型对比走 deep-comparison，调研借鉴走本 skill。
- **与 `comm-link-debugging` 互补**：后者是"通信链路排查定位"的方法论，本 skill 是"调研借鉴"的方法论。
- **可作为设计/选型的前置**：在 `tech-selection-convergence` 选型或 `guide-and-manual` 落地前，用本 skill 看业界怎么做，能让选型/设计站在业界肩膀上。

## 实践参考（一次完整演练）

机器人遥控协议设计中，两次"业界实践调研对照"是本 skill 的完整演练：

**演练一：切换控制模式时旧维度如何归零停止**
- ① 聚焦："切换时，上一模式控制的维度如何可靠归零，避免被保持导致非预期运动？"
- ② 对象：Unitree Go2、Loona（反编译可得）。
- ③ 采集：逐家挖"切换时旧控制怎么停"——Go2 全字段状态帧每帧覆盖、机器人运动服务自行接管（证实）；Loona 全字段 + 松手发零值帧 + 退出命令码带 ACK（证实）。严格标注"客户端能证实 vs 运动服务侧看不到"。
- ④ 对照表：对象 × 维度（载荷范式 / 停止表达 / 切换时旧控制 / 退出急停 / 通道 / 新旧判定）。
- ⑤ 共识：**两家都不用"字段省略=保持"，都全字段**——这是共识（该抄）。短板：都靠机器人侧仲裁、反馈弱。
- ⑥ 建议：抄"全字段"（推动决议从"字段省略"改为"全量携带+未控置0"）；避"反馈弱"（自定未控规则 + 强退兜底）。

**演练二：动作触发、执行/结束反馈、动作期间禁止操作**
- ① 聚焦："一次性动作指令怎么触发、怎么知道执行/结束、动作期间怎么禁止用户操作？"
- ② 对象：Go2、Loona。
- ③ 采集：Go2 动作走独立命令路径带 eventId 等回包（证实）、`inAction` 是 dead state（证实，全库无读取）；Loona 动作走独立子码 102 单发（证实）、完全无 ACK（证实）。
- ④ 对照表：动作路径 / 反馈 / 完成信号 / 期间锁输入 / 取消。
- ⑤ 共识：**两家都把动作走独立离散命令、不混入连续控制流**（该抄）。短板：**反馈都弱**（Go2 无完成事件、Loona 无 ACK）、**动作期间都不锁输入**靠机器人仲裁（该超越）。
- ⑥ 建议：抄"动作独立路径"（走 discrete 通道）；避"反馈弱+不锁"（加 started/finished ACK + app 锁输入 + 机器人忽略连续流）；明确超越点。

两轮调研直接推动了协议决议（全量置 0、动作走 discrete + ACK + 锁定），且明确标出"超越业界短板"的地方。反编译 / Go2 / Loona 仅作为方法论的**实践参考**，不是方法论本身。

> 参考文档：`docs/robot-control/业界实践对照-Go2与Loona.md`、`docs/robot-control/机器人侧协议对接讨论清单.md §9`。
