从一段已完成（或告一段落）的工作中，识别**可复用的技术流程/方法论**，提炼为新的 skill；同时审查现有 skill（含自定义 command）是否需要更新。本 skill 是**管理 skill 体系的元 skill**——不产出业务文档，而是产出/维护 skill 本身。

---

## 何时使用

用户出现以下任一意图时触发：

1. **"把这次/刚才做的 X 提炼成 skill"** —— 显式要求把某流程固化
2. **"检查对话里有没有该提炼成 skill 的"** / **"扫一下有没有可复用的"** —— 要求扫描挖掘
3. **"现有 skill 有没有要更新的"** / **"skill 过时了吗"** —— 要求审查维护
4. **一次性全做**："看看这次工作有什么能沉淀成 skill 的，再看看现有 skill 要不要改"

通常在**一段工作收尾时**调用（功能完成/阶段完成/会话结束前）。

---

## 和其他 skill / 命令的区别（先分清，避免用错）

| 工具 | 提炼什么 | 存到哪 | 受众/用途 |
|------|---------|--------|----------|
| **session-memory distill** | 用户的**行为本能**（人怎么思考/工作/决策） | `session-memory/instincts/` | 让 Claude 匹配用户工作方式 |
| **skill-recap（本 skill）** | **技术可复用流程/方法论**（怎么做事） | `.claude/skills/` | 固化成可调用的 skill |
| 各业务 skill（guide-and-manual / dev-recap-docs / app-error 等） | — | — | 执行具体任务 |

**关键分界**：提炼的是"用户的工作习惯/思维模式"→ session-memory distill；提炼的是"一套可复用的技术步骤/方法论"→ 本 skill。前者关于**人**，后者关于**事**。

## 产出物

一份**候选报告**，含两类条目，**逐项等用户确认**后才能写入：

### A. 新 skill 候选

每个候选给：
- **名称**（kebab-case，放进 xxy plugin 的 skills/ 或 commands/，无需 `xxy-` 前缀——namespace `xxy` 已提供归属）
- **一句话定位**（解决什么问题、何时触发）
- **与现有 skill 的区别**（和哪个重叠？为什么不是扩展那个而是新建？）
- **大纲**（何时用 / 产出 / 方法论要点 / 模板骨架）
- **可复用性证据**（这次出现了，为什么下次还会出现）

### B. 需更新的现有 skill / command

每个给：
- **目标 skill/command 名**
- **更新类型**（过时修正 / 补充缺失 / 方法论演进 / 触发词扩充）
- **具体更新点**（哪段、改成什么、为什么）
- **证据**（本次对话哪处暴露了该更新）

## 方法论（6 步，核心是"逐项确认"）

### 1. 扫描对话——识别"可复用流程"信号

回溯当前对话，找符合**全部三条**的流程：
- **反复出现**（不是一次性操作；或虽一次但明显是通用套路）
- **有固定步骤**（不是即兴发挥，而是可描述的 N 步流程）
- **下次还会做**（换个场景/项目仍适用）

信号举例：
- 用户多次要求同类产出（"给我对比表"、"生成检查清单"、"出调试文档"）
- Claude 反复执行同一套步骤（读现状→对比→产出→验证）
- 某个调试/排查套路被验证有效（值得固化）
- 用户纠正过 Claude 的做法（隐含应有更优的标准流程）

> 🔭 **识别贯穿全程的高层编排需求（易漏）**：扫描不能只盯"做了什么单点动作"，还要看"贯穿全程的元需求"。信号：用户**多次问同类问题**（如反复问"确认干净/确认无遗漏"）、主线任务反复执行同一套编排、多个单点流程其实是同一更大流程的子环节。这类往往是**编排层 skill（高于单点流程）**——只盯单点最容易漏掉它。例：单点的"遗留代码处置""版本库卫生"之上，还有贯穿全程的"工作区一致性核查"。

> ⚠️ **排除一次性内容**：只为本次任务服务的具体决策、项目特定的事实、临时方案——不提炼。

> **无自身豁免**：skill-recap 是元 skill，但**自身不豁免**——用户调用本 skill 时，skill-recap 自身与其他 skill 平等，纳入第 4 步"审查现有 skill"。skill 无法自主触发"自审"，但用户调用时它可以（且应当）被作为审查对象。

### 2. 通用化——剥离场景，提炼方法论

把流程从"本次具体场景"抽象为"通用方法论"：
- **剥离**：项目名、具体技术（如 MQTTS/WebRTC/Hilt）、具体文件名、具体常量
- **保留**：步骤结构、判断原则、产出形态、检查维度、避坑要点
- **实例降级为参考**：本次场景作为"实践参考"附录，不进方法论正文

**失败信号判定（强制）**：如果方法论的**正文**（非"实践参考"附录）出现领域专有名词——具体协议栈层级（如"网络→ICE→DTLS"）、具体工具名（如 tcpdump/GStreamer）、具体技术名——就是**没通用化够**。把这些名词移进"实践参考"附录，正文用抽象指代替换（如"该层的原生可观测信号""对端环境自带的探针"）。

**跨域复述验证（强制）**：把每个步骤用**完全不同领域**的词汇复述一遍（如把 WebRTC 联调换成 API 对接/软硬件协同）。任何一步必须换成另一领域术语才讲得通的，说明那步还绑着场景，要再抽象。

检验：把方法论套到"另一个完全不同的场景"，还讲得通吗？讲不通就没通用化够。

### 3. 去重对照——读现有 skill，避免重复

`Glob` 所有可用 skill 的 SKILL.md（含 plugin skills 与项目 standalone skills）+ 读每个 description/何时用，对照候选：
- **完全覆盖**？→ 不新建，改为"在报告中说明已由 X skill 覆盖"
- **部分重叠**？→ 候选里注明"和 X 重叠 Y，差异在 Z"，让用户选（新建 / 扩展 X / 合并）
- **完全独立**？→ 新 skill 候选

同时扫所有可用 command（含 plugin commands 与项目 standalone commands，或用户提到的 /xxy:* 命令），同样去重。

### 4. 审查现有 skill——对话是否暴露了更新需求

逐个看现有 skill（含 command），对照本次对话：
- **过时**：skill 描述的流程/约定和现在实际做法不一致了（如决策反转、流程演进）
- **缺失**：skill 漏了某个重要维度/步骤（本次踩坑暴露的）
- **方法论演进**：本次有了更好的做法，skill 该升级
- **触发词不足**：用户用了某种说法但没触发对应 skill（补触发词）

### 5. 出报告——候选清单，不写入

按"产出物"格式输出全部候选（新 skill + 需更新 skill）。**只输出，不写文件**。

### 6. 逐项确认后写入（红线：禁静默）

- 逐条问用户：**创建 / 更新 / 调整措辞 / 否决**
- 新 skill 候选确认时，**一并选定集成模式**（见下方"集成架构决策"）
- **复杂/高层候选的写作计划确认（中间步）**：对复杂或高层 skill 候选，报告大纲不足以授权写入——先呈现**详细写作计划**（章节结构 + 每章要点 + 需用户拍板的设计决策），用户确认计划后再写入。即确认分两级：**报告方向确认 → 写作计划确认 → 写入**。简单候选仍可报告级确认后直接写入。
- 用户明确确认的，才 Write/Edit 对应 skill 文件
- **引用同步**：写入前，若新/改 skill 引用了其他 skill（"与其他 skill 的关系"、集成链接等），核对引用名与**体系当前实际名字**一致。skill 体系会演进（重命名/拆分/合并），按记忆或旧目录名引用会过时、链接失效——用 Glob/ls 当前 skills 目录核对
- 未确认 / 否决的，不写
- 写入后报告：已写入哪些、用户否决了哪些

**写入授权以每个 skill 为单位**：当某个 skill 的**所有修订内容都被认同、且无补充或纠错待处理**时，该 skill 才可写入。讨论中的"同意"是方向认可，**不等于写入授权**——写入须等用户对该 skill 显式说"写入"。**一个 skill 的状态不影响其他 skill**：A 还在纠错，不阻塞已定稿的 B 写入。

### 集成架构决策（第 6 步确认新 skill 时一并选定）

第 6 步确认一个**新 skill 候选**时，若它与现有 skill 存在方法论重叠或关联，**一并决定它如何融入现有 skill 体系**。

四种集成模式：

| 模式 | 含义 | 适用 |
|------|------|------|
| ① 独立、无引用 | 新 skill 独立存在，不互链 | 与现有 skill 无方法论重叠 |
| ② 独立 + 被现有 skill 链接 | 方法论只存新 skill 一处，现有 skill 加链接（**不复制内容**） | 与现有 skill 共享方法论内核 |
| ③ 扩展（并入现有 skill） | 新内容写进现有 skill | 新内容是现有 skill 的自然延伸 |
| ④ 合并 | 多个相关 skill 合成一个 | 现有多个 skill 高度重叠 |

**链接优于复制（默认 ②）**：两个 skill 共享方法论时默认用链接（单一事实来源）——复制会漂移（更新只改一处），链接全局生效；仅当两处确需各自独立演化时才复制。落点：被引用方加一句指向链接（如"X 遵循 `Y` skill 的纪律，不在本文重复"），不复制 Y 的内容。

## 第二阶段：skill-recap 自修订（普遍更新写完后触发）

skill-recap 的方法论本身不完备。**不论本次产出的是哪个 skill 的更新，应用 skill-recap 过程中暴露的、需要用户额外纠正的不足**——Claude 被纠错之处、方法论未覆盖的情形、措辞/落点反复返工——**都反映 skill-recap 自身的缺口**。这些缺口只在普遍 skill 更新讨论**跑完后**才完整浮现，因此自修订是**独立的第二阶段**，不混入第一阶段。

**触发条件**：第一阶段（6 步核心 + 第 6 步集成架构决策）写入完成。

**动作**（复用 skill-recap 自身方法论，闭环）：

1. 回看本次整轮，收集所有"用户额外纠正"和"方法论没接住"的点
2. 每点作为一个 skill-recap 自修订候选，出报告（更新点 + 证据 = 本次哪处对话暴露）
3. 逐项确认 → 写入 skill-recap

**扫描充分性（强制）**：逐个工作流环节（拟定项措辞 / 报告 / 确认 / 写入 / 集成架构 / 自修订）问"这里有没有摩擦或被纠正"，不一次"看到没有"就结论"没别的缺口"。对每个浮现的缺口，按红线 5 的澄清判断归属，不按表面"像不像行为失误"归类。

**触发方式**：第一阶段写入完成后**自动**询问——"本次应用暴露了 N 个 skill-recap 自身缺口，是否进入第二阶段自修订？"（不靠用户记得触发）。

> 与第 4 步"审查现有 skill"的区别：第 4 步在讨论**前**，只能抓 skill-recap **内容过时**（基于已知信息）；第二阶段在讨论**后**，抓**应用暴露的缺口**（讨论中才发生）。两者不冲突。

## 红线（不可违背）

1. **禁止静默写入**——所有新 skill / 更新必须先出报告、逐项等用户确认，未明确确认的不写文件；**写入授权以每个 skill 为单位**（详见第 6 步），讨论中的"同意"不等于写入授权
2. **禁止提炼一次性内容**——只为本次任务服务的具体决策/项目事实/临时方案，不提炼为 skill
3. **禁止不通用化**——候选 skill 必须剥离场景（项目/技术栈），方法论能套到其他场景；方法论**正文**不得出现领域专有名词（协议栈层级/工具名/技术名），实例仅作"实践参考"附录；必须通过第 2 步的"失败信号判定 + 跨域复述验证"才算通用化够
4. **禁止不去重**——必须读现有 skill/command 对照；完全覆盖的不新建，部分重叠的让用户选新建/扩展/合并
5. **禁止混入行为偏好**——用户的思维/工作习惯归 `session-memory distill`（instincts），本 skill 只管技术流程（skills）。**但不要过度应用**：一个失误若其**具体表现落在 skill-recap 的工作流环节上**（拟定项措辞 / 报告 / 确认 / 写入 / 集成架构 / 自修订），它是**程序规则**不是行为偏好，应作为 skill-recap 修订候选，不归 session-memory；只有与 skill-recap 工作流无关的纯个人习惯才归 instincts。
6. **禁止凭空编造可复用性**——候选必须基于本次对话真实出现的流程，有证据，不臆想"可能有用"
7. **禁止未理解精确就给措辞/推进**——给每个拟定项措辞前，先复述"它针对什么、与相邻拟定项差在哪"，确认理解精确；有疑义先问用户，不自行补全。"认同方向"不等于"对该项的理解已精确确认"。

## 实践参考（一次完整提炼）

**本次会话**提炼 `dev-recap-docs` 的过程，就是本 skill 的一次落地：

1. **扫描**：发现本次产出了 MQTTS 手机侧数据流文档 + 实测避坑清单 #13–#22，是可复用的"开发收尾文档化"流程
2. **通用化**：把"MQTTS 信令数据流"抽象为"数据流逐步分解（代码+数据+log+检查点+卡点）"，MQTTS 降级为实践参考
3. **去重对照**：读 `guide-and-manual`（前瞻教实现）和 `code-to-doc`（软工图），确认本候选是"实现后回顾自查"——独立，不重叠
4. **审查现有**：`guide-and-manual` 无需更新（定位仍准），仅说明互补关系
5. **出报告 + 确认**：呈现候选，用户确认后写入 `dev-recap-docs`

以上是本 skill 的一次实例，**不是方法论本身**。下次扫描别的对话时，套用本 skill 的 6 步方法论即可。

## 完成后的后续动作（提示用户，不自动执行）

- 新建的 skill 若通用，提示可迁移到全局 `~/.claude/skills/`（跨项目）
- 若提炼出多个相关 skill，提示可考虑建立 skill 间的引用关系（A 的"区别"章节链 B）
- 走 `/xxy:session-memory save` 把本次提炼记录进会话记忆（skill 变更属重要进度）
