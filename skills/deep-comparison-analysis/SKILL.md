对两个技术选项做**严谨的优劣势对比**并收敛结论。本 skill 是一套**对比分析纪律**——解决"对比时容易混着比变量、被外部论据带偏、优势脱离项目规模"这三类常见失真。方法论通用，不绑定场景与技术栈；可作为 `tech-selection-convergence` 的**对比分析内核**被引用（那里定义"比什么/产出什么"，本 skill 定义"怎么严谨地比"）。

---

## 何时使用

- 用户问"X 和 Y 哪个更好 / 对比一下 / 为什么用 X 不用 Y / 本质区别是什么"
- 一次选型里列出了候选方案，需要严谨对比而非罗列利弊
- 对比已陷入争议、各方各执一词（往往是混了变量或被外部论据带偏）
- 也可被 `tech-selection-convergence` 在"方案对比"阶段显式调用

**不用**：单方案论证、纯事实查询、不需要收敛的开放讨论。

---

## 核心问题：对比为什么会失真

三个高频失真模式，本 skill 的六步纪律逐一对应：

| 失真模式 | 表现 | 对应纪律 |
|---------|------|---------|
| 混变量 | 把两个独立变量一起比，归因错位 | ① 拆变量 ② 控变量公平比 |
| 被外部论据带偏 | 用"错误写法/未来扩展/现状便利/从众"当本质优劣 | ③ 剥离外部论据 |
| 优势脱离规模 | "更省/更快"却不放到本项目规模下看是不是舍入误差 | ⑤ 规模校准 |
| 为推荐硬撑 | 已有倾向，对比时回避对自己不利的轴 | ④ 找本质差异 ⑥ 诚实收敛 |

---

## 方法论（六步）

### ① 拆变量

把两个选项间的**所有差异**拆成**独立维度**，逐个列出，不混着比。

- 典型坑：把"打包（batching）"和"编码（encoding）"两个独立变量放一起比；把"工具链成本"和"运行时性能"混为一谈。
- 检验：每个维度能否单独回答"这个差异归因于谁"，不依赖别的维度。

### ② 控变量公平对比

固定其余变量、**只变一个**，给每条差异标注**真实归因**（差异归因列）。

- 反例（不公平）：方案 A=单条发送、方案 B=批量+二进制，同时改了"批量"和"编码"两个变量 → 看不出各自贡献。
- 正例（公平）：先把"批量"固定（都批量），只比"编码"；再把"编码"固定，只比"批量"。
- 公平对比表必须有"差异归因"列，标注每行差异来自哪个变量。

### ③ 剥离外部论据

拿掉**非本质**论据，只留技术内在差异。常见要剥离的四类：

| 外部论据 | 为什么不是本质 |
|---------|--------------|
| 错误写法 | "用错 API 导致多一次拷贝"是实现失误，不是选项本身的属性 |
| 未来扩展性 | "将来可能上 Z"是预测，不是当前两选项的差异 |
| 现状便利 | "现在已经是 X，改要动 3 行"是迁移成本，不是 X/Y 谁更好 |
| 从众 | "业界多用 X"是文化，非技术 |

剥离后剩下的，才是两选项真正的内在差异。

### ④ 找本质差异

剥离完外部论据，剩下的**不可还原差异**是什么？往往薄到出乎意料——一个字段、一个标签、一个常量。

- 把本质差异浓缩成一句话："两种本质就是 ____"。
- 如果浓缩不出一句话，说明 ①② 还没拆干净。

### ⑤ 规模校准

把每条"优势"放到**本项目的实际规模**下看：是**决定性优势**还是**舍入误差**。

- 给量化判断：优势的绝对量级（字节/秒、毫秒/秒、KB 内存）放本项目频率/数据量/链路带宽下，是否还能被测出来。
- 典型：一条 100 字节消息、50Hz 频度下，省 50 字节 = 2.5KB/s——在视频级链路旁是舍入误差；在低功耗无线链路上可能决定性。
- 同一个"优势"，换个规模可能从决定性变可忽略，反之亦然。**脱离规模的"更优"没有意义。**

### ⑥ 诚实收敛

该认输就认输。如果某个选项在**当前前提**下（确定的规模、确定的数据形态、正确实现）全面更优，直接说它更优，**不为"推荐一致性"硬撑**。

- 检验：如果把前提翻转（如"数据永远不变"），结论是否也翻转？是 → 说明结论依赖前提，把前提讲清楚即可，不必回避。
- 反模式：之前推荐过 A，现在分析发现 B 更优，为了不"打脸"而强行给 A 找理由。

## 与其他 skill 的关系

- **被 `tech-selection-convergence` 引用**：那里在"方案对比"阶段链接到本 skill，作为"怎么严谨地比"的分析内核；那里定义"比什么"（5 个维度）和"产出什么"（决策三文件）。**纪律内容只存本 skill 一处**，避免重复与更新不一致。

- **与 `comm-link-debugging` 互补**：后者是"通信链路排查定位"的方法论，本 skill 是"对比收敛"的方法论。

## 实践参考（一次完整演练）

WebRTC 控制通道 DataChannel 载荷编码格式选型（string PPID 51 vs binary PPID 53，及 protobuf / 高频打包的延伸讨论）是本 skill 的一次完整演练：

- ① 拆变量：把"打包（batching）"与"编码（encoding）"拆开（用户纠正"混着比"暴露此步必要）
- ② 控变量：都打包后只比编码，发现"事件降 10 倍"是打包的功劳、不是编码的
- ③ 剥离：拿掉"错误写法（手补 \0 的多余拷贝）""未来扩展（protobuf）""现状便利（已是 binary）"
- ④ 本质：塌缩到"只差一个 SCTP PPID 标签字段"
- ⑤ 规模校准：50Hz/100B 下，省的字节和 CPU 在视频级链路旁是舍入误差
- ⑥ 诚实收敛："纯文本数据下 string 在性能/内存/语义/调试四轴全胜"——直接认输，不硬撑 binary

参考文档：`docs/robot-control/WebRTC连接/DataChannel数据格式选型-string与binary.md`。文中 WebRTC 仅作为方法论的**实践参考**，不是方法论本身。
