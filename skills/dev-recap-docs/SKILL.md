代码开发告一段落后，回顾**已完成代码 + 开发过程**，生成文档帮人**理解运行脉络**或**自查代码逻辑**。本 skill 从一次实践（MQTTS 信令层：[`MQTTS手机侧数据流.md`](../../../docs/robot-control/MQTTS手机侧数据流.md) + 手册实测避坑清单 #13–#22）提炼出**通用方法论**，不绑定场景与技术栈——任何功能/阶段/bug 修复告一段落均可套用。文中 MQTTS 仅作**实践参考**，不是方法论本身。

---

## 何时使用（先和其他 skill 区分，避免用错）

| 用户意图 | 用哪个 skill |
|---------|-------------|
| "决定用 X 实现 Y，给指南+手册教我怎么写" | **guide-and-manual**（决策时前瞻，教实现） |
| "从源码生成流程图/时序图/类图" | **code-to-doc**（软工图） |
| **"开发完了/告一段落，生成文档帮理解/给新人看/回顾自查代码逻辑"** | **本 skill**（实现后回顾，理解+自查） |

**本 skill 的触发场景**：
- 一个功能/阶段刚做完，要让没参与的同事看懂"代码怎么跑的"
- 自己过段时间怕忘，要回顾自查"逻辑对不对、有没有边界遗漏"
- 联调踩了一堆坑，要把"现象→根因→修复"沉淀下来别再踩
- 代码和旧文档对不上了，要以代码为准重新生成

**和 guide-and-manual 的本质区别**：那个是"**事前**"——决策时产出指南+手册指导别人实现；本 skill 是"**事后**"——实现完从代码+过程回顾，产出文档帮理解运行 + 自查逻辑 + 记实测坑。两者互补：前瞻教写，回顾教查。

## 产出物（3 类，按需选或全套）

| 文档 | 读者 | 核心问题 | 形态 |
|------|------|---------|------|
| **数据流自查文档** | 未参与者（理解）+ 开发者（自查） | 一次完整运行从入口到出口，数据怎么流转、每步在哪段代码、预期表现是什么、卡点怎么定位 | 逐步分解（代码位置+数据+预期 log+检查点+卡点分析） |
| **逻辑自查清单** | 开发者（自查） | 代码逻辑有没有错、边界/异常/时序/资源漏没漏 | 分类检查表（逐项 ✓/✗） |
| **实测避坑清单** | 所有人（理解+预防） | 开发中真踩了哪些坑、现象是什么、根因在哪、怎么修 | 编号表（# / 现象 / 根因 / 修复 / 代码位置），编号贯穿文档 |

三者可独立产出，也可成套。**数据流文档**是核心（既教理解又供自查）。

## 方法论（6 条，通用）

### 1. 现状摸清——动笔前必须读够，不凭印象

文档质量取决于输入。动笔前找齐：
- **代码**：入口点（哪个方法/按钮/事件触发）、核心类、数据流主干、状态机、关键分支
- **变更记录**：`git log` / `git diff`（本次开发改了哪些文件、为什么）
- **开发过程痕迹**：会话记忆（`.claude/session-memory/`）、调试 log、踩坑笔记、决策讨论
- **既有文档**：相关决策文档、设计文档（对照，标差异）

缺材料就标 `⚠️ 待补`，**不编造**。

### 2. 双受众视角——同时写"理解"和"自查"

每段内容问两个问题：
- **新人能看懂吗？**（运行脉络、为什么这么设计、概念清晰）
- **开发者能自查吗？**（逻辑对不对、边界覆盖、有没有遗漏）

数据流文档天然兼顾两者：逐步分解既教理解（怎么跑），又供自查（每步对不对）。

### 3. 数据流逐步分解——核心方法

选一条**端到端完整路径**（如"用户点连接→建连成功"），从入口到出口分解：

```
触发点 → 步骤① → 步骤② → ... → 完成
```

每步含 5 要素（缺一不可）：
1. **代码位置**：`文件:行号` 或 `类.方法`（可点击跳转）
2. **动作**：这步做什么（一句话）
3. **数据流转**：输入什么、输出什么、发到哪/收自哪
4. **预期表现**：logcat/终端/UI 该看到什么（具体，不写"应该成功"）
5. **检查点**：这步怎么算对、怎么算错

最后加：
- **总览图**（ASCII/Mermaid，标各步 + 数据流向）
- **卡点分析**：如果这步卡了，可能原因 + 怎么定位（实测最有价值）
- **对端/外部依赖**：这步依赖什么外部条件（其他系统/团队/配置）

### 4. 自查清单分类——别漏维度

逻辑自查按维度分类，逐项可验证（✓ 通过 / ✗ 有问题 / ⚠️ 待验）：

| 维度 | 检查什么 |
|------|---------|
| **正确性** | 主流程逻辑对不对、算法/状态转换有没有错 |
| **边界** | 空值/极值/首末次/并发/重复触发 |
| **异常** | 失败路径、错误传播、资源清理（try/finally）、超时 |
| **时序** | 顺序依赖、回调线程、竞态、先后约束（如 A 必须在 B 后） |
| **资源** | 内存/连接/文件句柄释放、生命周期、泄漏 |
| **约束对齐** | 是否符合项目既有约定（架构/DI/错误处理/日志/序列化） |

### 5. 实测避坑——只记真踩的，编号贯穿

避坑清单**只收开发中真实遇到的坑**（有现象/日志佐证），不编造"理论上可能踩"的坑。每条：
- **编号**（#1, #2…，跨文档一致，代码注释可引用 `避坑 #N`）
- **现象**：报什么错/什么异常表现（贴实测 log 片段）
- **根因**：为什么会这样（底层原因，不是表面）
- **修复**：怎么解决（代码怎么做）
- **代码位置/阶段**：对应哪个文件/阶段

> 实测坑的价值远高于理论坑——它是"真的会犯的错"，不是"想象中可能犯的错"。

### 6. 代码为唯一事实来源——文档与代码不符，以代码为准

事后文档最忌"文档说 A 但代码是 B"。生成时：
- 每个描述都要能指到具体代码（`文件:行号`）
- 发现文档（含自己以前写的）和代码矛盾，**改文档不改代码**（除非代码是 bug），并标注差异
- 状态/字段/签名等事实，从代码提取，不凭记忆

## 第一步：选路径 + 摸现状

1. **和用户确认要文档化哪条路径/哪个功能**（如"连接建连流程"、"配网流程"、"某 bug 修复"）
2. **读代码**摸清主干：入口 → 核心类 → 数据流 → 状态 → 输出
3. **读 git log / 会话记忆**找踩坑和决策
4. **告诉用户找到了哪些材料、缺哪些**，再动笔

## 模板

### 模板 A：数据流自查文档

```markdown
# {功能} 数据流（调试检查清单）

> 帮理解运行脉络 + 自查代码逻辑。对照 logcat 逐步核对。

## 一、总览图
[ASCII/Mermaid 数据流图：触发→各步→完成，标数据流向]

## 二、逐步分解（代码 + 数据 + 预期 + 检查点）

### ① {步骤名}
- **代码**：`文件:行号` / `类.方法`
- **动作**：做什么
- **数据**：输入/输出/收发方向
- **预期 log**：具体输出
- **检查点**：怎么算对

### ② ...（重复）

## 三、卡点分析
每步"如果卡了"的可能原因 + 定位方法（实测最有价值）

## 四、对端/外部依赖
这流程依赖什么外部条件（其他系统/团队/配置/协议对齐）

## 五、当前状态（实测）
```

## 约束与红线

1. **禁止凭印象写**——所有描述（API 签名/字段/状态/常量）必须来自代码或实测 log，不用通用知识填充
2. **禁止只写 happy path**——数据流必须含失败/超时/异常分支；卡点分析是核心价值
3. **禁止编造避坑**——避坑清单只收真踩的（有现象佐证），理论坑不收
4. **禁止文档落后于代码**——发现矛盾改文档（标差异），不以旧文档为准
5. **禁止破坏现有抽象**——文档描述代码现状，不改代码（除非用户确认是 bug）
6. **代码位置必须可点**——`文件:行号` 或 `类.方法`，读者能跳转核对
