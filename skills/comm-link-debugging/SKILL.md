调试跨系统中**通信/数据传输链路**的集成问题，自己只掌控一端、对端不可见时使用。本 skill 是一套**通信链路联调方法论**——跨系统调试中最常见的一类：处理"对端是个黑盒、只掌控己侧"时最容易踩的坑。

> **范围声明**：跨系统调试不止通信链路，还包含数据一致性、多模块时序、跨团队契约理解差异、软硬件状态同步等**非通信**问题——那些不在本 skill 范围。五步里，②跨端交叉对撞、③己侧极限转读对端、⑤给对端最低成本诊断 对非通信跨系统也通用；①分层原生信号验证、④可达性原理 偏通信/协议栈链路。

---

## 何时使用

- 通信链路联调卡住：客户端↔服务端、手机↔设备、软硬件之间的数据通道、跨网/跨服务传输
- "对端说发了，但我没收到" / "我发了，对端说没收到"
- 卡在协议某一层（网络？握手？传输？应用语义？）分不清
- 对端是另一个团队/系统/AI/厂商，你只能看到己侧

**不用**：单系统内部 bug（用 `app-error`）、纯己侧代码逻辑问题、非通信的跨系统问题（数据一致性/时序/契约差异等）。

---

## 核心原理：可达性/正确性不可跨层传递

通信链路按协议栈组织。**某一层"通/对"不蕴含相邻层"通/对"**——每层有自己邻层看不见的失效模式。

**通用反例（协议无关）**：

| 下层"通/对" | ≠ 上层"通/对" |
|-----------|--------------|
| 网络层可达（ping/路由通） | 传输层通（端口可达） |
| 连接建立 | 握手成功（如 TLS） |
| 加密层通 | 应用协议被正确解析 |
| **传输层确认收到（ACK/SACK）** | **对端应用层实际处理（onMessage/业务逻辑）** |
| 接口返回 200 | 业务语义实际成功 |
| 硬件枚举到 | 驱动正常响应 |

→ 验证怀疑层，必须用**怀疑层自己的原生可观测信号**，不能用邻层信号代理下结论。

---

## 方法论（五步）

### ① 分层定位 + 原生信号验证

把通信链路按协议栈分层，定位失败可能发生在哪层，用**那一层自己的原生信号/工具**验证。因为"通/对"不跨层传递（见核心原理）。

- 禁止用邻层信号代理："ping 通了所以网络没问题"——ping 是网络层（ICMP），不通的是传输层（UDP/TCP），两回事。
- **己侧应用层调用底层 API 别假设成功**——检查返回值/成功标志。典型：`send()`/`publish()` 返回的 Boolean 被忽略，应用层误判"已发"，实际没入队（缓冲满/状态瞬变）。返回值就是该调用跨越边界的原生成功信号，不查等于盲发。
- **最底层用协议字节/包内容验证**——应用 log 看不出时，开底层库 verbose log，直接解析协议包（chunk type/字段值）判断数据流向与握手状态。比应用层 log 更原生、更难骗人。
- 分层验证表逐层填：层 / 原生信号或工具 / 结果（通/不通/未知）。

### ② 跨端交叉验证

（对非通信跨系统也通用）对端（另一团队/系统/AI/厂商）给出的结论，拿来和己方运行时证据**逐条对撞**，找矛盾。真根因常在矛盾处。

- 单方结论既不轻信也不直接否定——用证据对撞定位。
- 典型：对端说"网络不可达/无 pair 连通"，己方日志却有"对端的成功响应（code=0/rtt=X）"——后者只能是对端发的，矛盾即线索。
- 对端的"协议层判断"也要对撞：对端说"这是 X 类型的包"，己方解析字节发现其实是 Y（如把 STUN 包误判为数据通道包）——以字节为准。
- 矛盾对照表：对端说法 / 己方证据 / 是否矛盾 / 矛盾指向。

### ③ 己侧到极限 → 转读对端实现

（对非通信跨系统也通用）当己侧已无更多可观测/可调项（该看的日志看了、该改的开关试了、返回值都查了），把排查重心转到**对端的实现**（源码/配置/日志），因为问题大概率在对端。

- 标记"己侧可调项清单"并标到极限——避免在己侧反复空转。
- 读对端代码找 bug，但注意第 ④ 步。

### ④ 运行时优先于静态产物

（偏通信链路：协议参数/配置常对不上）手上的源码/配置/声明**未必是实际运行的版本**。任何"代码里写着 X"的结论，必须用**运行时证据**（运行日志/抓包/探针输出）证实，否则可能对着过时/未生效的静态产物空排查。

- 典型：源码写 640×480，运行实际输出 320×240 → 源码≠运行的二进制。
- 三处以上独立矛盾（分辨率/帧率/参数级别都对不上）→ 几乎可断定"给的源码不是跑的"，停止对着它排查，要运行态证据。

### ⑤ 给对端最低成本诊断

（对非通信跨系统也通用）球在对端时，设计一条对端用**最低成本**就能跑、且能**一锤定音分流根因方向**的诊断指令（用对端环境自带的探针/抓包/日志开关），跑一行即可把根因收敛到几个方向，避免靠猜来回。

- 反例：让对端"重新检查整个管线"——成本高、反馈模糊。
- 正例：一条 `tcpdump` / 调高某模块日志等级 / 一个内置探针开关，输出能直接分流（"有出包→发送侧没问题""无出包→发送侧问题"）。
- 每条诊断标注：跑什么、能分流到哪几个根因方向。

## 实践参考（一次完整演练）

WebRTC MQTTS 跨网联调（手机 app ↔ 机器人 GStreamer webrtcbin，经云端 broker 信令）是本 skill 的一次完整演练：

- ① 分层：网络（ping/路由）→ ICE（STUN binding）→ DTLS（握手）→ SRTP（解密）→ 媒体/数据应用，逐层用对应层日志证实；"ping 通 ≠ ICE 通"；最底层解析 SCTP 包字节（chunk type INIT/DATA/SACK）确认数据流向；检查 `dc.send()` 返回值别假设成功
- ② 交叉验证：机器人 AI 说"无 pair 连通/网络不可达"，手机侧却有"STUN response code=0 rtt=7ms"（只能机器人发的）→ 矛盾即线索 → 真根因在对端候选处理（SKIP mline=1 + 无 BUNDLE）；对端把 STUN 包误判为独立数据通道，己方解析字节纠正
- ③ 己侧到极限：手机侧 ICE/DTLS/SRTP 全通、解码器就绪、DC OPEN、`send` 返回 true、无可调项 → 转读机器人 recv.c
- ④ 运行时优先：recv.c 写 640×480@15fps，运行实际 320×240 + framerate:30 + level 不符 → 源码≠运行的二进制
- ⑤ 最低成本诊断：给机器人 `GST_DEBUG=x264enc:6`（看 slice 数）+ `tcpdump udp and host <手机IP>`（看出包）——一行分流"是发送侧没发包，还是包发了手机没收"

参考：项目记忆 `webrtc-mqtts-debug-checkpoint.md`、`docs/robot-control/09_agent_webrtc/recv.c`。文中 WebRTC 仅作为方法论的**实践参考**，不是方法论本身。
