# workspace-consistency — 工作区一致性核查与收尾编排

## 何时使用
- 一段工作收尾（功能完成 / 阶段完成 / 会话结束前）
- 开始新开发前，确认开发空间干净
- 用户问"还有什么需要同步归档的""开发空间干净吗""确认无遗留"

## 和现有 command 的区别（防重复）
- `app-change-save`：完成工作后**提取沉淀知识**（会再犯的坑 / 会再用的模式）—— 知识层
- `app-phase-save`：**执行**更新进度记忆文档；`app-readme`：**执行**更新说明文档 —— 执行者
- 本 skill：**核查**"文档是否过时 / 代码是否同步 / 变更是否有记录 / 有无遗留"，过时则**指引调用**上述命令；不重复执行
- 收尾时三者可能都做：**先本 skill 核查一致性 → 调对应 command 修复 → 最后 app-change-save 沉淀知识**

## 产出
一份**四维度核查表**（每维度 通过/不通过 + 证据）+ **编排待办**（每项不通过 → 对应修复动作）。全维度通过 = 开发空间干净。

## 方法论：四维度核查

> 建议顺序「可追溯 → 文档同步 → 无遗留 → 版本库整洁」（先确认变更都有记录，文档才好跟上），但不强制。

### 维度 1：变更可追溯
- 列出本次工作产生的代码变更，逐个查是否有**对应变更记录**（变更归档 / PR / issue）
- 核查问题：**"有没有代码已改、但没留下记录的裸变更？"**
- 典型不通过：一批代码已写完测试通过，但没有对应的变更记录（事后归档场景）

### 维度 2：文档与代码同步
核查四类文档是否反映代码**当前**状态：
- **进度记忆文档**（记录阶段进度 / 技术决策）：进度标注是否过期（标"待开发"实际已完成、标"未归档"实际已归档）
- **规格文档**（描述系统契约 / 行为）：描述的方案是否还是代码在用的（文档说 A 方案，代码已改 B）
- **说明文档**（README / 新人指南）：是否过时
- **审查清单 / 选型决策文档**（代码审查方案、`软件决策与约束/` 决策文）：⚠ 其**规则性条目**（"必须 X / 禁止 Y"）在架构/契约变更后会从"过时描述"升级为"**错误审查依据**"——比普通过时更危险，会误导后续 PR 审查。架构变更后**优先扫**这类文档的规则条目
- 核查问题：**"文档里描述的状态（尤其规则性条目），代码还是这样吗？"**
- 典型不通过：规格文档落后代码一两步；架构变更后审查清单仍列旧模型规则（例：传输层从双通道改单通道，审查清单仍要求"急停走 reliable 独立通道"→ 误导审查）

### 维度 3：无遗留 → 遵循 `legacy-code-disposition`
核查有无 dead code / 半成品 / 未接通逻辑 / 长期 TODO / 不确定还要不要的代码。处置决策（删/接通/保留预案）走 `legacy-code-disposition` 的方法论，本 skill 不重复。

### 维度 4：版本库整洁 → 遵循 `repo-hygiene`
核查工作树是否 clean、有无误入库内容（第三方/大文件/嵌套仓库/本地配置）、提交粒度是否合理、ignore 规则是否生效。清理走 `repo-hygiene` 的方法论，本 skill 不重复。

## 编排修复（不通过 → 动作映射）
| 不通过维度 | 修复动作（指引，不亲自执行）|
|-----------|--------------------------|
| 变更有裸改无记录 | 走项目变更归档流程**补录**（如事后归档一个 change）|
| 文档过时 / 失同步 | 调 `app-readme`（说明文档）/ `app-phase-save`（进度记忆文档）；**审查清单/决策文档的规则性条目**失同步 → 调 `app-change-save`（规则修正）或手动改正 |
| 有遗留代码 | 调 `legacy-code-disposition` |
| 版本库不整洁 | 调 `repo-hygiene` |

修复后**重回核查**确认该维度通过（复核，不止查一次）。

## 干净判据
四维度**全通过** = 开发空间干净，可开始新开发。任一不通过则先修复再确认。

## 红线
- **禁跳过核查直接开发**——开发前必过四维度（至少快速过一遍）
- **禁把执行动作写进本 skill**——保持对账层纯粹，执行归被引用的 skill/command（否则会与方法论来源漂移）
- **禁只核查不复核**——修复后必须重回核查确认通过，不能"查过就算"

## 实践参考：一次完整核查（已脱敏）
用户两次问"还有什么需要同步归档的，确认开发空间干净"，四维度逐一命中：
1. **变更可追溯**：发现一批代码改动（含视频接收 + 信令层重构）无变更记录 → 事后补录归档一个 change
2. **文档同步**：规格文档描述的旧信令方案，代码已换新方案 → 追平主规范；进度文档标"某流程未归档"实际已归档 → 修正过时表述
3. **无遗留**：发现一段"算了没用"的代码 → 走 `legacy-code-disposition` 判定删除
4. **版本库整洁**：发现误入库的大量第三方文件（已跟踪，ignore 无效）+ 嵌套仓库 + 本地配置 → 走 `repo-hygiene` 清理

四维度修复后复核通过，工作树 clean，开发空间干净。

以上是一次实例，不是方法论本身。
