# repo-hygiene — 版本库卫生

## 何时使用
- 准备提交，想确认没误入库内容
- "gitignore 加了规则怎么不生效"
- 发现仓库里有第三方代码 / 反编译产物 / 嵌套仓库 / 大文件 / 密钥 / 个人本地配置
- 开始新开发前，确认版本库整洁

## 产出
干净的版本库：无误入库内容、提交粒度合理、ignore 规则正确生效。

## 核心坑（先记这条）
**ignore 规则只对未跟踪文件生效。已跟踪的文件加 ignore 无效——必须先移除跟踪(保留本地)再 ignore。**
这是"gitignore 不生效"最常见原因：文件早已提交入库，事后加规则挡不住已跟踪的。

## 方法论

### 1. 识别不该入库的内容类型
| 类型 | 识别特征 |
|------|---------|
| 第三方/反编译/生成产物 | 别人的代码、反编译、构建输出（通常量大） |
| 嵌套仓库 | 目录内自带版本库元数据，被当 gitlink（模式 160000）提交 |
| 个人本地配置 | .local 后缀、本机路径、个人密钥 |
| 二进制大文件 | 图片/压缩包/数据包/模型 |
| 密钥凭据 | .env / *.key / token |

### 2. 分层验证手段（按需用）
- `status`：变更概览
- `check-ignore <path>`：该路径是否被某 ignore 规则挡住（无输出=没挡住）
- `ls-files <path>`：该路径是否**已 tracked**（有输出=已入库，ignore 对它无效）
- `status -uall`：展开折叠的 untracked 目录（中文路径/整个目录都未跟踪时，普通 status 会折叠藏起）

> 判断"加 ignore 有没有用"：先 ls-files 看是否已 tracked。已 tracked → ignore 无效，走第4步移除跟踪；未 tracked → ignore 直接生效。

### 3. 检查 ignore 规则本身
- 规则路径是否写错（多了前缀字符、大小写、斜杠方向）——写错的规则**静默失效**
- 目录规则用尾斜杠 `path/`，文件规则无尾斜杠

### 4. 处置
| 情况 | 动作 |
|------|------|
| 已 tracked 的不该入库 | 移除跟踪(本地保留) + 加 ignore：`git rm --cached -r <path>` 然后 commit |
| 未 tracked 的 | 直接加 ignore |
| 嵌套仓库（gitlink） | 先识别（模式 160000 + 无 modules 配置 = 悬空 gitlink），三选一：① ignore(本地参考) ② 转正式子模块 ③ 去掉内部版本库当普通文件入库 |

### 5. 提交粒度
代码 / 文档 / 配置 / 清理 分开提交，历史清晰、可独立回退。不要一个大提交混所有类型。

### 6. 开发前整洁检查
- 工作树 clean（无未提交改动）
- 无待入库的 untracked 文件（除本地参考）
- 无悬空 gitlink
- ignore 规则正确（误入库的已移除跟踪）

## 红线
- **禁用"全量暂存"前不核查**——会把误入库内容（尤其大文件/第三方）一起提交
- **禁只加 ignore 不移除跟踪**——对已 tracked 文件无效（核心坑）
- **禁删本地文件**——清理用"移除跟踪(保留本地)"，不是物理删除

## 实践参考：一次仓库瘦身（已脱敏）
1. 加 ignore 规则后发现"反编译目录仍显示"→ ls-files 发现**已 tracked（约 1.4 万文件）**→ ignore 无效
2. 原 ignore 规则路径前误加字符致静默失效 → 修正规则
3. 嵌套仓库（对端代码 clone）被当悬空 gitlink 提交 → 移除跟踪 + ignore（本地参考保留）
4. 个人本地权限配置（.local）反复变动 → 移除跟踪 + ignore
5. 分多个提交：代码 / 文档 / 清理分开

以上是一次实例，不是方法论本身。
